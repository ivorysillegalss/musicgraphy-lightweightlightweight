## R-111 · 爬取限流对策专项（MusicBrainz 503 墙与单源依赖）

### 背景实况锚点

- B10 mb-calibrate 三遇 MB 503 墙（pass2/pass3；1b74890 披露 pass3 failed 41；累计
  year 103 / country 105 / genres 12，剩余约 67 行未定；卡现置 **blocked** = 815a736）。
- **MusicBrainz 无 API key 体系**：Web Service 按 IP 平均限速（官方口径 ~1 req/s 连续平均）；
  503 = 服务端拒绝，共享出口 IP（NAT）信誉会加剧（1b74890「对 IP 加剧」实测结论）。
- **数据面实况（2026-11-16/17）**：本环境 data/ DB = 11-13 前快照（netease=0 行、
  user_version=1），B5 正式导入与 pass1–3 成果在旧机 DB 未随迁 → 增量重跑无从执行，
  待用户裁决 **DB 搬运 vs 重导入**（815a736 blocked 披露）——R-111 的执行前置裁决。
- 现有降级链 = MusicBrainz→Deezer→iTunes→Discogs（**搜索**）；但**权威化回填
  （year/country/genres）当前单挂 MB**——单源依赖即本专项的靶心。

### 目标

1. netease 导入行的元数据权威化不再被单一上游限流卡死：补全链路在任一单源不可用时仍可达。
2. 全站爬取面（搜索/封面/预览/权威化）在限流常态下可持续，限流纪律红线零突破
   （全局串行 ≥1s、全局 30/min、源专属预算如 iTunes 20/min、显式 UA）。

### 技术候选（六案，评审案定稿取舍）

| # | 候选 | 要点 | 倾向 |
|---|---|---|---|
| ① | 字段级多源权威化回退 | MB 缺位/被墙时由 Deezer/iTunes/Discogs 补 year/genres/country；各源字段质量差异逐源实测留证；权威冲突取舍规则 | **主案候选** |
| ② | 用户自有 API key/token 池（BYO key） | 有官方 key 体系的源接用户级凭据（Discogs token 匿名 25/min→token 60/min、Last.fm apikey、Spotify OAuth）；**MB 无 key 体系 = 对 MB 本身不适用（诚实结论）**；按用户存 key 与 R-112 天然契合 | 与 R-112 联动 |
| ③ | 调度优化 | 夜间批窗口、指数退避、失败重试队列、连续 503 熔断（已内置单次退避，缺熔断）、批次进度持久化 | 低风险先行 |
| ④ | 出口 IP 轮换/代理 | **灰色项**：涉隐私红线边界与上游 ToS——须用户裁决，默认不推荐 | 待裁决 |
| ⑤ | 本地 MB 数据库副本（官方 dumps） | 全量 dump 数十 GB + Postgres 引入，对个人 SQLite 应用失衡 | 倾向拒绝 |
| ⑥ | 缓存与增量续跑补强 | 现状已 resumable；补负缓存（miss 不重打）、批次计划持久化 | 低成本补强 |

### 验收标准（草案）

- 剩余 ~67 行（+未来增量）补全路径明确且不依赖 MB 单点可用性；
- 任一源 503/不可用时 year/country/genres 补全仍可经备选源推进；
- 限流纪律零突破（任何限流参数改动逐项留证）。

## R-112 · 多用户账户系统（架构级需求）

### 用户指示原文

「当前我希望这个网站存在账户系统，所有人都有他自己的账户，以及后续的专辑收藏的
不同维度的个人信息。」

### 需求要点

1. **账户体系**：注册/登录，每人独立账户。V10 单密钥登录（ACCESS_KEY 环境变量 +
   HMAC cookie 会话）升级为多用户会话（会话绑定 user_id）；密码存储候选
   node:crypto scrypt（零依赖，Node 内置）。
2. **每用户独立收藏空间**：collection_record / tags / note 等按 user_id 绝对隔离。
   数据模型地基已在档：各表 user_id 列 + UNIQUE(user_id, album_id) 约束 +
   DAO userId 参数习惯（贯穿程度精确清单 = 评审案核查项）——多用户并非零基础。
3. **收藏的不同维度个人信息**（开放定义，须用户澄清后评审定稿）：候选维度 =
   用户资料（显示名/头像）/ 收藏统计仪表（metrics 域已有雏形）/ 年代·流派偏好画像 /
   每用户 saved-views（现按 user_id 归属待核）/ 每用户 BYO key（R-111②）。

### 架构影响面（评审案必答）

- 鉴权改造：注册/登录/会话绑定/CSRF 沿革（V10 表单+Origin 校验语义保留）。
- DAO/SQL 全查询 user_id 过滤补全：精确列出未带 userId 的查询（评审案核查项）。
- 迁移：存量 'local' 数据归属方案（owner 账户接管）。
- 隐私红线升级：跨用户绝对隔离 = 档案默认私有；外部元数据可共享、用户数据绝不跨账户。
- 产品定位修订：「个人音乐档案」→「多用户的个人档案集合」——定位表述修订 +
  与 02-变现文档包 04B 增长方案关联（多用户 = 方案 B 增长验证的基础设施候选），须用户裁决。
- 与 R-103 React 接入协同：登录/注册页与动效分期（S2-3 评审案 P2 纯 CSS 批可先行的衔接）。

### 开放问题（评审案必答）

- Q1 注册形态：开放自助 vs 邀请制 vs 单管理员建号（个人实例的攻击面与运维成本）
- Q2 存量 'local' 数据归属（owner 账户方案）
- Q3 密码找回通道（邮件 = 新外部依赖，隐私红线与运维成本评估；或无找回=诚实披露）
- Q4 「不同维度的个人信息」具体维度清单（用户澄清后进评审）
- Q5 多用户与既有单用户假设的冲突清单（topster 分享、export、封面缓存共享面等）
