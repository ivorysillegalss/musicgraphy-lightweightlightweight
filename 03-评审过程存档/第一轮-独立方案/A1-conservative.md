# A1 档案管理员 · 第一轮评审

评审立场声明：我按"砍掉它，产品是否依然成立？"检验每一个候选功能。本方案的目标是概念数量净增为零、P0 全部落在 Record/Find 主干、把行业惯性建议尽可能挡在门外。凡是我拿不准的，一律降级或进"不做"清单——少做错事比多做对事更重要。

---

## A. 对现有产品目标的评价

### A1. 优点（4 条）

1. **闭环自洽，且给了裁决机制。** 5.8 明确"如果一个产品功能不能加强这条核心链路，就不应该成为 Musicgraphy 2.0 的核心能力"，AGENTS.md §16 给出冲突排序 `Find → Record → Organize → Review → Discover`。这两条把"做不做"从品味问题变成可裁决问题，是全文档最宝贵的资产。档案类产品死于功能蔓延，裁决条款就是防腐剂。
2. **"Collection 是事实，View 是观察"的分层正确。** 5.5 明确 View 不制造新数据、只重组 Collection；AGENTS.md §9 禁止 Topster 产生第二套状态。这保证展示需求永远无法反向污染档案结构——这是档案系统长期不腐坏的结构性保证。
3. **已有明确的"不做"边界。** 5.7 列出七条不追求的方向，AGENTS.md §3 列出 MVP 暂不实现清单，§13 列出不默认建立的页面。大多数产品文档只说做什么，这份文档敢于说不做，起点正确。
4. **记录成本的定位准确。** 5.1 把"几秒钟完成一次记录"设为标准，并把数据库信息与个人信息严格分离（AGENTS.md §4 数据原则）。档案的第一敌人是录入摩擦，这个判断抓住了要害。

### A2. 盲点（4 条）

1. **"用户数据是资产"缺少落点。** AGENTS.md §4 说"用户数据必须被视为用户资产，任何同步机制都不得无条件覆盖"，但产品目标全篇没有任何一条提到导出或备份。一个承诺"长期积累"的档案，如果档案本身不可带走、不可备份，这个承诺就是单方面的。这是档案管理员视角下最刺眼的缺口。最小修补是设置页一个导出按钮，不需要引入任何新概念。
2. **Find/Record 缺少可检验的验收口径。** 5.3 说 Find 是最重要的目标，5.1 说"几秒钟内完成一次普通记录"，但两者都没有定义什么程度算达标（几步操作？多少秒？失败率多少？）。没有口径，最高优先级就只是口号，开发时也无法判断"做到位没有"。
3. **listenedAt 的时间语义未定义。** 5.5 的 Review 依赖"某一年听过什么"，AGENTS.md §4 列出了 addedAt 和 listenedAt 两个字段，但没有任何文档回答：listenedAt 默认等于 addedAt 吗？可以补录历史吗？"记录时间"和"收听时间"的语义含糊，在数据积累两三年后会变成无法回补的数据债务。数据模型的模糊必须在使用早期消除，越晚越贵。
4. **未定义重复记录的防线。** 5.1 只讲添加多快，没讲"这张我是不是已经记过了"。重复记录是档案的直接噪声，伤害档案的唯一性与准确性，这是档案质量底线问题，文档没有覆盖。

### A3. 风险（3 条）

1. **执行漂移风险：View 被写进核心目标，又被工程文档排除在 MVP 之外。** 5.8 的最终定义里出现"Topster、Timeline、Map 等不同 View"，而 AGENTS.md §3 明确 MVP 不做 Map/Timeline。两份文档的张力若不裁决，开发中最容易发生的事就是"顺手把 View 做了"——而每个 View 落地都会带来入口、状态、管理面，复杂度必然回潮。需要明确：View 是 P2，且每个 View 独立裁决，绝不打包评审。
2. **Tag 熵增风险。** 5.4 鼓励用户建立自己的分类语言，但没提同义 Tag（夜晚/晚上/late night）分裂怎么办。MVP 不需要治理工具，但"输入时展示已有 Tag"这种零成本的归并手段不应推迟——Tag 数据一旦分裂，治理成本随存量线性增长。AGENTS.md §7 把自动补全列为"后续"，我认为这是把该在数据产生时解决的问题推迟到了数据已经污染之后。
3. **大规模状态下的默认体验未被定义。** 5.2 要求几千张时产品仍可用，但文档只讲了搜索筛选；Recently Added 默认页在几千张时只展示最近一小段，"翻看全库"的体验是什么没有答案。这个空白未来一定会被"文件夹/分组/智能列表"类提案填补——每一条都是新概念。应预先用既有概念（排序扩充、筛选组合）回答，而不是等新概念提案出现。

## B. 我的产品理念（一句话）

**Musicgraphy 2.0 的成败不取决于新增什么，而取决于把"搜索→确认→添加"和"筛选→找到"两条路径打磨到零摩擦，并把一切 View 严格关在 Collection 之上——档案的全部价值来自每一条记录在几年后仍然找得回来。**

---

## C. 方案清单

### C0. 功能挖掘总判断

四层闭环本身已经完备，**不需要新增任何一级产品概念**。值得做的全部是两类工作：(1) 把 MVP 清单中 Record/Find 相关项打磨到位并给出验收口径；(2) 修补档案质量与数据语义的缺口。以下每条都通过"砍掉测试"——标注砍掉后闭环是否成立。

### C1. P0 必须做（5 条，全部在 Record/Find 主干）

**P0-1 三步记录路径做到极致**
- 内容：`搜索（部分匹配/联想）→ 确认 → 添加` 三步完成；添加动作不弹表单，落库后在详情页或小卡片上从容补 Favorite/Tag/Note。
- 推理链：5.1（记录成本尽可能低、不打断听音乐）+ AGENTS.md §5（输入→候选→确认→添加优先于复杂语法）。Record 是两大最高任务之一。
- 砍掉测试：不可砍，这是产品本体。

**P0-2 渐进式筛选器**
- 内容：Genre / Year 区间 / Favorite / Tag 四个维度的组合筛选，结果实时更新，与 Collection 同屏。
- 推理链：5.3（最重要的产品目标）给出的用户记忆场景（"2010 年左右的电子""夜晚标签"）恰好对应这四个维度；AGENTS.md §5 支持渐进式过滤。Find 是最高优先级。
- 砍掉测试：不可砍。几百张之后没有筛选的集合必然失效，Find 目标直接落空。

**P0-3 Collection 内搜索与"已收藏"标注**
- 内容：同一个搜索框服务两种意图——搜外部数据源（想记录）与搜自己的 Collection（想找回）；结果中明确标注"已收藏"。
- 推理链：5.3（收藏之后找不到）+ AGENTS.md §5（搜索是一级能力）+ §6（需快速判断是否已收藏）。用户"我记过吗"和"我想记它"是同一动作的两个分支，拆成两个搜索反而增加概念。
- 砍掉测试：不可砍，这是 Find 与 Record 的交汇点。

**P0-4 Tag 自动补全（输入时展示已有 Tag）**
- 内容：Tag 输入框直接下拉展示已有 Tag，支持点选，可同时新建。
- 推理链：5.4（低成本 Personal Tag）+ AGENTS.md §7（Tag 保持低成本输入）。它同时服务记录速度（少打字）与档案卫生（归并同义 Tag）。我把它从"后续"提进 P0 的理由：这是唯一一个"现在不做、以后无法廉价补救"的功能——Tag 分裂的治理成本随存量线性增长，而实现成本是一个下拉框。
- 砍掉测试：砍掉后闭环成立，但数据债务不可逆，属于"砍掉会留下永久暗伤"的例外，故进 P0。

**P0-5 记录与找回路径的可靠性口径**
- 内容：给 Record/Find 定验收标准——普通记录 ≤ 3 步 / 15 秒；搜索数据源失败、候选为空、网络慢三态各有明确体验（可重试、可手动建议、不丢已填内容）。
- 推理链：5.1（"几秒钟"需要变成可检验标准，修补 A2-2 盲点）+ AGENTS.md §15（loading/empty/error 是完成标准）。一次失败的添加比慢 0.5 秒更伤害记录意愿，可靠性就是记录成本本身。
- 砍掉测试：不可砍，它是 P0-1/P0-2 的质量定义。

### C2. P1 应该做（5 条，服务档案质量与 Organize）

**P1-1 档案导出（JSON/CSV，元数据+用户数据）**
- 推理链：AGENTS.md §4（用户数据是资产）+ 5.2（长期积累承诺）。修补 A2-1 盲点。砍掉测试：通过（闭环仍成立），但"个人档案"的承诺打折；成本是一个接口一个文件。这是全方案唯一的"目标延申支线"，见 C4。
- 体现给用户的方式：设置页一个"导出我的档案"按钮，无新页面、无新对象。

**P1-2 listenedAt 语义确定：默认 = addedAt，允许轻量修改**
- 内容：记录时不强制填；详情页一行可把"最近一次听"改掉或补录历史年份，除此之外不做任何时间管理功能。
- 推理链：5.5（Review 依赖"某一年听过什么"）+ 5.1（用户决定"什么时候听过"）。修补 A2-3 盲点。为什么 P1 而非 P0：Review 层尚未启用，但字段语义必须先于数据积累确定，这是典型的"越晚越贵"的数据模型决策。

**P1-3 排序扩充第二档：Oldest Added / Release Year**
- 推理链：5.2（长期积累后的浏览效率，修补 A3-3）+ AGENTS.md §6（"后续可以支持"列表中点名了这两项，且"不要在 MVP 引入大量排序"）。一次只加这两个，加完即止。为什么 P1：几千张后"最早期"是高频回顾诉求，但排序数量本身是认知成本。

**P1-4 防重复提示**
- 内容：添加前若专辑已在 Collection，明确告知"已收藏"并提供跳转，不产生第二条记录。
- 推理链：5.2（档案准确性是质量底线）+ AGENTS.md §6（是否已收藏要能快速判断）。修补 A2-4 盲点。为什么 P1 而非 P0：它是防噪声防线而非主干路径，但实现上会随 P0-3 的"已收藏"判断一并落地，产品上独立验收。

**P1-5 空态与首次引导**
- 内容：Collection 为空时展示三步说明；首次添加 Tag 时给两三个示例。无新手教程、无弹窗向导。
- 推理链：5.1（第一次记录必须顺畅，第一次失败最容易流失）+ AGENTS.md §12/§15。砍掉测试：通过，闭环不受影响，故 P1。

### C3. P2 可探索（2 条，全部是 Review 层 View，各自独立裁决、不打包）

**P2-1 Topster**
- 内容：`Collection → 筛选 → 封面网格`，可导出图片；不做自由画布、不做布局保存。
- 推理链：5.6（玩具属性的主要来源）+ AGENTS.md §9（View 不产生第二套数据）。砍掉测试：通过——没有 Topster 闭环完整成立，它服务表达欲而非找回。且它引入"保存哪些 Topster"的状态问题，必须等 Collection 稳定后再裁决。
- 体现给用户的方式：Collection 筛选结果页上的"生成封面图"动作，无新导航层级。

**P2-2 Timeline（按 Release Year / addedAt 的纵向浏览）**
- 推理链：5.5（重新浏览音乐历史）。砍掉测试：通过。它本质是"排序+按年分组"的另一种渲染，若 P1-3 做好，增量成本低；但仍应晚于核心。

**P2-3（最低位，可再砍）回顾的自然发生**
- 内容：不建统计页，把回顾缝进既有页面——Collection 顶部一行只读文字"你本月记了 N 张"，或"三年前的今天你添加了……"。
- 推理链：5.5（回顾）+ 5.7（不新增概念）。它无新概念、纯只读，但属于"新鲜感"型功能，与档案的恒定气质略冲突，放最低位并附加约束：无推送、无通知、无独立页面。若团队精力不足，第一刀砍它。

### C4. 目标延申支线

我判断 2.0 **只许可一条延申支线**，其余一律不延申：

- **支线（唯一许可）：档案的"可带性"。** 从"在我这里积累"自然延申到"我的档案我持有"。体现方式：设置页的导出按钮（即 P1-1）。许可理由：它不新增任何产品概念——没有新页面、新对象、新状态，只是把 §4"用户数据是资产"的既有承诺落成文件；它是 5.2"长期积累"承诺的必要保险，不是新方向。
- **不延申的论证：** 其他一切常见支线（导入同步、评分、统计报告、推荐发现、社交分享、移动端）都要求新增数据源、新概念或新的信任机制，逐一违反 5.7 复杂度条款。"不延申"之所以是正确决策：这类单人档案工具的留存引擎是"档案在用我"——每次使用让档案更有价值，积累本身产生黏性；延申功能服务的是拉新与日活，会稀释这条唯一叙事。正确的增长策略是深用（用得更久、档案更厚），不是广用（用得更多）。判断依据始终是 5.8：不加强核心链路的，不进核心。

## D. 明确不做清单（16 条）

1. **地图 / 地理聚类 / 国家维度**：地理只是专辑的一个属性，"靠国家找回忆"的真实场景极少，而 geo 缓存与聚类的维护成本远超其找回价值（5.7 + AGENTS §2/§10）。
2. **Last.fm / Spotify 自动导入同步**：自动同步消解了"记录"的有意识动作，档案会混入大量用户并不在意的内容，稀释档案价值；同步覆盖与 §4 用户资产原则天然冲突。
3. **1–10 评分体系**：Favorite 已覆盖"最爱"的找回需求；评分引入"每张都该补分"的义务感，直接抬升记录成本（AGENTS §8 已明确此立场，我确认它）。
4. **统计 Dashboard / 年度报告页**：回顾应轻量地缝进既有页面；Dashboard 是后台管理系统的视觉语言，违反 §12，且砍掉它闭环完整。
5. **社交 / 好友 / 分享流**：不在定位内；社交会把记录动机从"为自己"扭曲为"为展示"，腐蚀档案的真实性。
6. **推荐 / Discovery Pool**：需要外部数据与算法概念，直接违反 5.7；"发现新音乐"不是本产品要解决的问题。
7. **智能播放列表 / 规则式动态分组**：这是第二套分类体系，与 Tag 语义重叠；"筛选+排序"的组合已能覆盖绝大部分场景。
8. **文件夹 / 合集实体**：Tag 的劣质重复，概念数量 +1 却不增加任何找回能力。
9. **复杂搜索语法（AND/OR/引号/字段限定符）**：用户的记忆是模糊的，语法要求精确记忆，方向相反；渐进筛选就是答案（AGENTS §5）。
10. **移动 App / 多端**：Web 单端先验证闭环；每多一端，维护成本与概念漂移风险成倍增加。
11. **歌曲 / 曲目级记录**：产品定义是 Album Archive；曲目级会引来播放、歌词、时长等流媒体边缘需求，边界失控的入口。
12. **AI 自动生成 Tag / 简介**：自动生成的内容不属于 5.4 定义的"用户自己的分类语言"，会污染 Tag 语义；AI 辅助可作远期实验，不进 2.0。
13. **协作 / 共享 Collection**：共享意味着权限系统，等于提前平台化，违反 AGENTS §11。
14. **Topster 自由画布 / 排版编辑器**：一旦可自由编辑就要保存布局状态，产生第二套数据，违反 §9；Topster 的价值是筛选结果的视觉表达，不是设计工具。
15. **通知 / 推送 / 每日提醒**：档案产品不制造使用义务；如果需要"提醒用户来记录"，说明记录成本还没降到位，该修产品而不是加推送。
16. **批量编辑（多选改 Tag）**：几百张以内逐张可忍；批量编辑 UI 的复杂度与误操作风险在档案早期不划算，等真实痛点出现再议。
17. **用户自定义封面 / 手改公共元数据**：允许修改会产生"本地事实"与"公共事实"的冲突，破坏 §4"外部元数据可同步修正"的前提。
18. **Discogs 式版本 / 压制 / 介质管理**：定位明确排除（AGENTS §2），那是另一个产品。

（注：原计划 16 条，落笔后为 18 条——清单只会变长不会变短，符合我的立场。）

## E. 推理过程总览

1. **起点：5.8 的最终定义。** "Record 让我愿意记，Find 让我找得回"是两大最高任务，Organize/Review 建立其上。这给了我第一把尺子：所有候选功能先按其服务的环节定位。
2. **检验工具：砍掉测试。** 对每个候选问"砍掉后闭环是否成立"。不成立的进 P0（主干做对）；成立但留下永久暗伤的进 P0/P1（导出、Tag 补全、时间语义属于此类——它们便宜且不可逆）；成立且无暗伤的进 P2 或不做（Topster/Timeline/回顾缝入）。
3. **P0 的构成原则：** P0 不含任何"新功能"，全部是 MVP 清单中 Record/Find 相关项的"做到位 + 验收口径"。理由：目标文档的功能设计已经足够，2.0 的失败模式是做不精，不是做不多。
4. **P1 的构成原则：** 全部是档案质量与数据语义的修补（导出、时间语义、防重复、第二档排序），每一条都对应我在 A2 列出的一个盲点。盲点修补优先于新能力。
5. **P2 的构成原则：** 只允许 View，每个独立裁决，绝不打包；并在 P2 内部再排序，留下"第一刀砍谁"的预案。
