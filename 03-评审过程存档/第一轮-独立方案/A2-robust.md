# A2 体验工程师 · 第一轮评审

> 人格参数：发散度 2/5（在既有概念内做深，不引入新的大概念）；稳定度 4/5（结论以工程与交互可行性为准绳）。
> 评审立场：Musicgraphy 2.0 的竞争力不来自新概念，而来自三个物理瓶颈被磨平——**输入成本、试错循环、扫视成本**。下面所有主张都从这三个词推导。

---

## A. 对现有产品目标的评价

### 优点

**A1. 优先级声明诚实且可执行。**
《产品目标》5.8 与 AGENTS.md §16 给出了明确排序 `Find → Record → Organize → Review → Discover`，且 5.7 给出了反向判据（"功能数量不是产品成熟度的主要指标"）。这不是口号，而是工程上可机械执行的验收标准：任何 PR 都能问一句"它加速了哪个环节"。多数产品文档死于目标不可判定，这份文档不会。

**A2. "外部元数据 / 用户数据"二分是正确的数据架构决策。**
5.1 与 AGENTS.md §4 把 Album Metadata 与 Collection Record 分离、把用户数据定义为资产，这决定了三件事：外部源可以随时换（last.fm 挂了、封面源换了都不伤档案）、View 不产生第二套状态（Topster 原则 AGENTS.md §9）、产品寿命与任何第三方服务的寿命解耦。对一个"以十年为单位积累"的档案产品，这是最重要的一条工程决策，且文档做对了。

**A3. 把"规模"写进了产品目标而不是留给工程。**
5.3 的"Collection 越大，搜索和筛选的价值越高，而不是收藏越多，产品越难使用"是一句可测试的产品级验收标准。它把 5000 张场景从"以后再说"提升为"设计约束"。

### 盲点

**B1. "几秒钟完成一次记录"没有被拆解，最大的隐藏摩擦是"输入"本身。**
一次记录 = 输入 → 辨认候选 → 确认 → （可选属性）。5.1 用数据源自动化解决了确认之后的成本，但完全没碰最贵的一步：在搜索框里打出专辑名。桌面全键盘打一个专辑名约 3–6 秒，移动端更贵；再加上拼写变体（feat.、大小写、外文标题）、同一专辑多版本条目要辨认，"几秒钟"在现有描述下是达不成的。**目标文档承诺了一个它没有设计过的速度。**

**B2. 模糊找回只给了能力清单，没有给交互形态，且漏掉了一种目标文档自己举出的记忆类型。**
5.3 列了 Genre/Year/Favorite/Tag 四个筛选维度，但没有回答：用户从哪个条件开始？筛选器是表单（下拉+勾选+应用按钮）还是即时 chips？加一个条件后如何知道"还剩多少张"？模糊记忆的本质是**试错式**的——先筛 Electronic，看到太多，才想起"封面好像是蓝色"。表单式筛选强迫用户一次性想全条件，与试错过程直接冲突。
更关键的是：5.3 自己举了"封面好像是蓝色的"这个例子，但四个维度没有任何一个能表达颜色记忆。**目标文档提出了一个它没有打算解决的问题。**（封面主色是可自动计算的派生元数据，不是新概念。）

**B3. "500→5000 张"的失效拐点没有被定义，Tag 的规模化问题同样没有。**
5.2 要求考虑长期增长的浏览效率与信息密度，但没有回答：纯封面网格在哪个量级开始扫视失效？列表失效后替代形态是什么？性能预算是多少？同样，Tag 的进化路径只写到"最近使用、自动补全、颜色"（AGENTS.md §7），没有处理两个必然发生的问题：Tag 膨胀（两年后 80 个 tag，一半只挂在一张专辑上）与同义分裂（"夜晚/夜间/night"）。在 5000 张规模下这两个问题会直接侵蚀 Find——Tag 一旦不可信，用户就不敢用 Tag 筛选了。

### 风险

**R1. Record 速度承诺落空 → 攒不下记录 → 不可逆流失。**
如果"记录快"只靠"字段少"实现，输入成本就是物理上限。用户会在某一次"懒得打字"后开始欠账，欠账积累的结果不是记录变慢，而是**停止记录**——而 Collection 的全部价值建立在记录发生过。这是整个闭环里唯一不可逆的环节。

**R2. Favorite 的信息熵在约 2000 张后耗尽。**
Favorite 是布尔值。收藏量大后用户会 Favorite 得越来越保守或越来越泛滥，两种情况都让 `Favorite = Yes` 失去筛选价值。AGENTS.md §8 拒绝评分体系是对的，但"拒绝评分"之后没有给 Favorite 的退化预案。实际证据已经出现：目标文档 5.4 里的"2026最爱"就是用户在用 Tag 顶替评分，Tag 系统将被迫膨胀。

**R3. 若筛选做成"应用式表单"，Find 的核心体验会整体走偏。**
交互形态选错一次，后面加再多筛选维度都救不回来——用户面对的还是一个需要先想清楚、再提交、失败了再重来的数据库查询页，而不是"边试边想"的记忆检索。这是本产品最不能返工的一个决策，值得在 MVP 期就锁定 chips + 实时计数的形态。

## B. 我的产品理念（一句话）

> **把两个动作磨到极限：一次记录不超过 5 秒，一次模糊找回不超过 3 次筛选加 10 秒扫视，并保证这两条在 5000 张时和 50 张时一样成立。**

产品的全部差异化都藏在这两句话里。不新增任何大概念，新增的是每个既有概念被做到的深度。

## C. 方案清单

### P0 必须做（MVP 内，缺一则核心承诺失效）

**P0-1. 记录提速三捷径：零输入候选、粘贴识别、已收藏前置标记**

- 推理链：5.1 "几秒钟完成一次记录" → 拆解为输入/辨认/确认三段 → 元数据自动化只覆盖了确认之后 → 输入段是剩余最大摩擦（盲点 B1）→ 必须降低"往搜索框里放什么"的成本。
- 具体设计：
  - **零输入候选**：搜索框获得焦点、未输入任何字符时，即显示候选——上次添加的艺术家及其专辑（连续记录同一艺术家的概率最高）、最近搜索词。打开即选，一次点击替代一次打字。
  - **粘贴识别**：允许粘贴任意来源文本——链接（Spotify/YouTube/RYM URL 提取 ID 或 slug）、标题字符串（"Artist - Album" 格式自动拆分匹配）。用户在听歌平台看到专辑时，复制粘贴是比键盘输入更自然的手势。这仍属于"搜索专辑"这个既有概念，只是把它做深（支持支线一，见后）。
  - **已收藏前置标记**：搜索结果里已收藏的条目在候选阶段就带标记，避免用户点进确认后才发现重复——重复检查本身就是记录摩擦的一部分（关联 P1-4）。
- 工程量：零输入候选 = 最近添加查询；URL 识别 = 字符串解析 + 一次搜索；无新服务、无新表。

**P0-2. Add 弹层"顺手三件套"：Favorite 开关、Tag 快速 chips、Note 可折叠**

- 推理链：5.1 "用户真正需要决定的，只应该是与自己有关的信息" → 这三类信息必须与添加动作发生在**同一个界面、同一个流程**，跳页即摩擦 → 5.4 的个人 Tag 多为高频复用（夜晚/通勤/夏天），所以 Tag 输入的主形态不是打字而是点击。
- 具体设计：
  - 添加确认弹层内含：Favorite 心形开关、Tag 输入框（上方常驻"最近使用的 5–8 个 tag"，点击即挂）、Note 折叠框（点开才出现文本域）。
  - **默认状态 = 点击"添加"即完成**，三件套全部可选、全部不阻塞关闭。单次点击路径与完整记录路径并存。
  - 允许"先添加，稍后补"：详情页随时可补 tag/note（Record 允许两段式，不强迫一次完成）。
- 工程量：一个弹层组件 + 最近 tag 查询。无新概念。

**P0-3. 渐进式筛选 = 常驻 chips + 实时计数 + 条件联动收敛**

- 推理链：5.3 "从多个已知信息逐步缩小范围" + "搜索是一级能力"（AGENTS.md §5）→ 模糊记忆是试错式循环"加条件 → 看剩多少 → 决定下一步"（盲点 B2）→ 筛选器的交互形态必须匹配这个循环，每加一个条件**立即**给出数量反馈。
- 具体设计：
  - Collection 顶部常驻一行可展开的筛选 chips：Genre / Year / Favorite / Tag /（P0-4 的 Color）。
  - 每个可选值旁显示当前命中数：`Electronic (86)`；每激活一个 chip，其余条件的计数立即重算，计数为 0 的选项自动隐藏或置灰。
  - 已激活条件显示为可单独移除的深色 chip，移除即回流。无"应用/重置"按钮——状态即所见。
  - 结果区域同步显示总数："37 张匹配"。
- 工程量：普通 SQL 条件组合 + count 查询，5000 张规模毫秒级，完全符合 AGENTS.md §11 "能通过普通查询完成的事情，不引入复杂索引或独立服务"。

**P0-4. 封面主色提取与色板筛选——回答"封面好像是蓝色的"**

- 推理链：5.3 自己举出的记忆类型（"封面好像是蓝色的"）在现有四个筛选维度下无解 → 封面颜色是外部元数据的**自动派生值**，提取在记录时一次性完成，用户零输入 → 它同时改善浏览（颜色是扫视封面时的第一识别特征）与找回，一条数据两个目标受益。
- 具体设计：
  - 记录/导入封面时提取主色，归入 12–16 个离散色板（红橙黄绿青蓝紫 + 棕灰黑白），存为 Collection Record 上的一个派生字段。
  - 筛选 chips 增加色板行：一排色块，点击即筛。
  - 不承诺精确颜色记忆，只承诺"从 3000 张缩小到 200 张蓝色系"这个量级的收敛——这正是模糊找回需要的。
- 工程量：一次批处理脚本 + 一个字段 + 一个 filter 选项。无 AI 依赖、无新概念。

**P0-5. Collection 密度三档 + 年份分组 + 性能预算（5000 张不降速）**

- 推理链：5.2 要求长期增长后的检索/浏览/信息密度 → cover-first 是正确默认，但纯封面网格的扫视成本随规模上升，且封面识别依赖记忆强度——记忆越模糊越需要文字辅助（盲点 B3）→ 密度档位让用户按当前记忆强度选扫视方式。
- 具体设计：
  - 三档密度：**大封面**（纯网格，玩具模式）、**中封面 + 标题**（默认，平衡）、**紧凑列表**（行式：封面缩略 + 艺术家 + 年份 + 标题，精确扫视用）。
  - "Release Year 分组"作为 MVP 唯一新增分组方式——它直接对应"2010 年左右"这类年代记忆（5.3 第一条用户原话），其它排序遵循 AGENTS.md §6 不铺开。
  - 性能预算写进验收：5000 张下首屏可交互 < 1s，滚动无白屏（虚拟滚动即可达成，属工程手段而非功能）。
- 工程量：一个网格组件的三个渲染模板 + 虚拟滚动。

### P1 应该做（MVP 后第一梯队，多为防退化与提速叠加）

**P1-1. Tag 轻治理：补全防分裂 + 低频 tag 合并提示**

- 推理链：5.4 + AGENTS.md §7 明确预留了"最近使用、自动补全" → 规模化后 Tag 的两个敌人是膨胀与同义分裂（盲点 B3），若不处理，Tag 失去筛选可信度，直接反噬 Find → 治理必须是**轻的**：不建管理后台、不建分类树。
- 具体设计：输入时自动补全已有 tag（预防"夜晚/夜间"分裂）；Tags 总览页对"只挂 1 张专辑"或"与另一 tag 字形高度相似"的 tag 给出一行式合并提示（点击选择合并目标，重定向引用）。每季度一次的低频打扰，换 Tag 体系长期可信。

**P1-2. 保存筛选组合为命名视图（Find → Review 的桥）**

- 推理链：5.3 的终态是"符合个人记忆方式的检索" → 高频用户会反复使用同一组合（夜晚 + 电子 + Favorite）→ 把当前 chips 状态保存为一个命名 query，等价于用户给自己沉淀了一套**个人检索语言** → 它与 Topster 同构：`Collection → Filter → 保存的视图`，View 不产生新数据，完全符合 AGENTS.md §9 的第二套状态禁令。
- 体现方式：侧栏"我的视图"列表；一键恢复筛选态。它同时成为 Review 的日常入口（点"夜晚"即回顾）。

**P1-3. Note 纳入 Collection 内搜索**

- 推理链：AGENTS.md §5 列出的记忆通道有"自己添加过的 tag"，但用户同样可能记得**自己写过的话**（"我在备注里写过 reverb 很重"）→ Note 是唯一由用户自由文本组成的字段，是模糊记忆的又一条检索通道 → 5000 条 note 的内存/like 遍历在工程上不值得优化，普通实现即可。

**P1-4. 重复记录的转化：防错动作变成整理动作**

- 推理链：Collection 到 3000 张后重复率上升 → 对已存在条目的"添加"动作若只弹"已存在"，是一次挫败；若转成"已在你 Collection 中 · 去补充 tag / note / 再听一次"，挫败就转化为 Organize 机会 → 同时服务 Record（不破坏记录心流）与 Organize 两个目标。

**P1-5. 桌面键盘流：/ 聚焦搜索、Enter 添加首个候选、F 快速 Favorite**

- 推理链：5.1 的速度承诺对高频记录者主要在桌面兑现 → 高频用户的记录动作是成串的（一次坐下来记 5–10 张）→ 键盘路径把单次记录压到 2–3 秒，工程成本接近于零。移动端不受影响。

**P1-6. 歌曲名反查专辑（Record 支线，见"目标延申支线"一）**

- 推理链：5.1 的输入成本 → 用户很多时候手里只有一首歌名 → 在"搜索"概念内做深：粘贴/输入命中歌曲时显示"所属专辑：XXX，记录该专辑？"→ 把"想起一句歌词/歌名也能记"变成现实，记录入口从"必须知道专辑"放宽到"知道任意粒度"。

### P2 可探索（验证核心模式后）

**P2-1. Favorite 内拖拽前 N 位。**
- 推理链：R2（Favorite 信息熵耗尽）的预案 → 不引入 Rating（守住 AGENTS.md §8），改为 Favorite 内部支持拖出前 3/5/10 位 → `My Top 25`（AGENTS.md §9 场景）直接获得数据来源，Favorite 重获表达力。

**P2-2. "N 年前的今天"回顾触点。**
- 推理链：5.5 Review → 完全建立在已有 addedAt 上，不产生新数据 → 体现方式：打开 Collection 时顶部一行低打扰小字"2 年前的今天你记录了《X》"，点击进详情。让档案"活着"的成本最低的一种方式。

**P2-3. 色带浏览 View。**
- 推理链：P0-4 数据的浏览面复用 → 与 Map/Timeline 同级的又一种"观察 Collection 的方式"（5.5），按主色排布封面墙。玩具属性 + 找回双通道。

**P2-4. Topster 导出图片。**
- 推理链：5.6 玩具属性 → 导出是 Topster 价值的兑现面（贴到社交平台的不是 Musicgraphy 本身，而是作品图），不引入任何社交功能。

**P2-5. listenedAt 的"大约年份"精度输入。**
- 推理链：5.1 用户可决定"什么时候听过" → 多数人不记得精确日期，提供"大概 2012"的年份级输入 → 为"我大一那年听的"这类时间记忆提供第四条找回通道，也为 Timeline 积累真实素材。

### 目标延申支线（不另起炉灶的四条自然延长线）

1. **Record → 任意粒度反查**：搜索入口接受歌名/片段/链接，命中后归约到专辑。体现方式：搜索框粘贴任意文本，出现"所属专辑"候选卡。本质是同一搜索能力的输入端放宽。
2. **Find → 个人检索语言沉淀**：保存的筛选视图逐渐成为用户自己的"记忆索引"。体现方式：侧栏"我的视图"，命名即沉淀（"深夜电子""大一那年"）。
3. **Review → addedAt 的日常触点**：当年今日。体现方式：Collection 顶部一行小字，无独立页面。
4. **Organize → Tag 生命周期轻提示**：年末对"2026最爱"类年份 tag 建议创建"2027最爱"。体现方式：Tag 自动补全里的一次建议。极轻，可不做。

## D. 明确不做清单

| 不做 | 理由 |
|---|---|
| 评分体系（1–10） | AGENTS.md §8；Favorite + P2-1 顺序已覆盖表达需求，评分引入填写摩擦直接违反 5.1 |
| AI 推荐 / 相似专辑 / Discovery Pool | 超出"个人档案"边界（AGENTS.md §2）；5.7 明确不做推荐系统 |
| Last.fm / 流媒体自动同步 | 同步进来的是"听过"不是"想留住"，会稀释 Collection 语义；AGENTS.md MVP 暂不实现 |
| 社交、评论、关注 | 与产品定位直接冲突；分享需求由 P2-4 导出图片满足 |
| Tag 层级 / 文件夹 / 树 | 5.4 "允许用户建立自己的分类语言"——结构化层级是强迫，不是解放 |
| 复杂搜索语法（AND/OR 查询语言） | AGENTS.md §5 "不构建复杂搜索语法"；chips 组合已覆盖 95% 场景 |
| 地图 / 地理维度 | AGENTS.md §10，旧 P2 能力不回潮 |
| 统计 Dashboard | AGENTS.md §13；回顾需求由 Review 支线（P2-2、视图）满足 |
| 多用户 / 权限 / 平台化 | AGENTS.md §11；当前是个人记录型产品 |
| 播放器功能 | 不做流媒体（AGENTS.md §2），外链到播放平台即可 |

## E. 推理过程总览

1. **起点是三个物理瓶颈，不是功能清单。** 把 5.1 与 5.3 的承诺翻译成用户侧的动作序列：记录 = 输入 → 辨认 → 确认 → 属性；找回 = 想起线索 → 筛 → 扫视 → 确认。逐段测量哪一段最贵：记录的瓶颈在"输入"（B1），找回的瓶颈在"试错循环有没有即时反馈"（B2）和"扫视方式是否匹配记忆强度"（B3）。方案 P0-1/2/5 攻记录，P0-3/4/5 攻找回。
2. **每个方案必须同时过两道校验。** 产品校验：能否指认它加速了四目标中的哪一个（AGENTS.md §2 的准入规则）。工程校验：是否只用了普通查询、派生字段、组件级改动（AGENTS.md §11 优先简单）。P0 五条全部通过——最重的 P0-4 也只是一次批处理加一个字段。
3. **防御性思维优先于扩张性思维。** 稳定度 4/5 决定了我的方案里"防退化"条目占比高：Tag 膨胀（P1-1）、Favorite 熵耗尽（P2-1）、重复记录挫败（P1-4）、性能预算（P0-5）。档案产品的风险不是缺功能，而是随规模腐化——5.2 的原话"长期积累"就是指这个。
4. **发散被约束在"做深"而非"做新"。** 全部方案没有引入一个新的产品对象：色板是元数据派生，命名视图是 query 保存，反查是搜索输入端放宽，当年今日是 addedAt 的展示。每一条都能回答"它建立在哪个已有概念之上"——这是 2/5 发散度下我认为唯一正确的创新方式，也恰好是 5.7 要求的方式。
