# A3 记忆研究员 · 第一轮评审

评审人格：用户记忆研究员型产品经理。研究人如何记住、又如何忘记音乐：感知记忆（封面颜色、专辑形态、某段旋律）、情境记忆（那个夏天、通勤路线、大学宿舍）、情绪记忆（深夜、失恋、第一次听到时的震动）。评审基准：任何功能必须对应一个具体的找回/回顾场景才成立。发散度 3/5，稳定度 3/5。

---

## A. 对现有产品目标的评价

### A1 优点

**优点 1：「模糊信息检索」的直觉在认知科学上是对的，且被放在了正确的位置。**
目标文档 5.3 承认用户"经常不是带着完整的信息寻找一张专辑"，并把搜索定为一级能力（AGENTS.md §5）而非附属功能。这暗合记忆提取的基本规律：对残缺记忆，正确策略是**最小化回忆（recall）、最大化再认（recognition）**——不要求用户说出完整答案，只要求用户在缩小后的候选集里"认出它"。多数音乐产品把收藏当列表管、把搜索当查找框；这份文档把"记忆残缺"当成第一性问题，这是 2.0 最有价值的判断。

**优点 2：Genre/Tag 的语义切分，实质上承认了"私人记忆语言"的合法性。**
5.4 "Genre 是音乐的属性，Tag 是用户的属性"——在记忆研究的语境下这句话非常准确：用户对专辑的编码是情境化、私人化的（"夜晚""大学""那个夏天"），强迫用户把私人感受映射成公共分类，等于强迫用户用外语回忆自己的经历。允许用户建立自己的分类语言，就是允许用户用自己的母语存储记忆。

**优点 3："Collection 是事实，View 是观察"保护了记忆的完整性。**
5.5 的数据观（View 不制造新数据）意味着用户档案不会被某个视图的需求扭曲。个人记忆不能被平台"重新组织出事实"，只能被不同方式观察——这个立场对个人档案类产品是稀缺且正确的。

### A2 盲点

**盲点 1：对"记忆残缺"的类型学覆盖不全——文档只建模了语义残缺，漏掉了时间指向混淆、声音记忆和 Note 线索。**
逐项检查 5.3 列举的残缺信息：
- "好像是一张 2010 年左右的电子音乐"——用户脑中的"2010 年左右"**经常指"我听的时候"，不是"它发行的时候"**。而筛选系统只有发行 Year；listenedAt/addedAt 在数据模型里存在（AGENTS.md §4），却没有进入 Find 的能力清单。文档自己举的第一个例子，没有被产品承接。
- "封面好像是蓝色的"——例子举了颜色感知记忆，但全部筛选示例（Genre/Year/Favorite/Tag）里没有任何颜色或视觉特征轴。感知记忆只有一句台词，没有戏份。
- Note 作为记忆载体在 Find 中完全缺席：用户在 Note 里写下的"天台""青旅""和谁一起"恰恰是三年后最独特的检索线索，但 5.3 与 AGENTS.md §5 的可搜索字段（标题片段/艺术家片段/年份/genre/tag/favorite）都不含 Note。**记忆写下来了，但没有接线。**

**盲点 2：把"找回"全部建模为"用户主动发起查询"，忽略了记忆唤起的另一半——触发。**
真实的记忆唤起大多是线索驱动（cue-driven）的：咖啡馆里听到一段旋律、朋友随口提了一个乐队名、年底忽然想"这一年我听了什么"。文档假设用户会带着线索打开筛选面板，但没有回答"什么时候会想到来翻档案"。Review 目标（5.5）列了用户"可能希望"回看的内容，却没有任何触发机制的设计。**没有触发时机的 Review，在行为上不会发生**——这会直接掏空闭环最后一环。

**盲点 3：编码侧盲点——找回质量取决于记录时埋了什么线索，文档对此只有半句话。**
5.1 追求记录零成本是对的，但记忆研究的基本事实是：**提取失败多数是编码失败**。一张"只留了 addedAt"的专辑，三年后只剩封面可认，"为什么留它"全部蒸发。文档在"用户真正需要决定的"清单里提到"什么时候听过或添加过"，却没有讨论两个真实问题：补记录行为（新用户头几天会批量补记旧爱，addedAt 全是同一周，时间线从第一天起失真）；听取时间如何以最低成本采集。编码问题被一笔带过，而它恰恰决定 Find 三年后的成色。

### A3 风险

**风险 1：情境记忆全押在 Tag 上，而情境记忆大多是"非意图编码"。**
用户添加专辑时通常不会想到"这是大学专辑"——这个归属是他两年后才意识到的。Tag 是需要当时有预见性的主动行为，注定只能覆盖一小部分情境记忆。更糟的是 Tag 词汇会漂移（"夏天"→"2019夏天"→"高三暑假"），用户自己都记不清当时打过什么词。如果 Find 的私人通道只有 Tag 一条，情境找回会系统性失效；而"听的时候（时间）"是系统唯一免费拥有的情境维度，目前却没有被 Find 使用。

**风险 2："记录即遗忘"——极简记录若不配最低限度的线索编码，Collection 会变成"没有记忆的记忆"。**
封面墙能让用户认出"我收过它"，却无法回答"它对我意味着什么"。当 Note 使用率低、Tag 覆盖稀疏时，"个人音乐记忆档案"的叙事会空心化：数据在增长，记忆没有在积累。这正是目标文档开头要对抗的"随着收藏数量增长而逐渐消失"——只是换了一种形式发生。

**风险 3：多轴渐进筛选与低复杂度目标的内在张力。**
5.3 要求 Genre×Year×Favorite×Tag 多轴筛选，若每轴都是表单控件，筛选面板会滑向"高级搜索表单"，与 5.7 低复杂度承诺冲突。渐进筛选的正确体验应当是"从一句模糊输入开始，每一步都在变小、始终看得见封面"，而不是"先打开一个表单"。这个张力需要正面设计解决，否则 Find 的增强会以伤害使用意愿为代价。

**风险 4：View 先于 Find 的旧病可能复发。**
Topster/Timeline/Map 都写在目标里，但若在 Find 未解决前铺开 View，会重复旧 P2 的教训——表达先于档案，视觉先于可用。AGENTS.md 已把 View 移出 MVP，这个约束应当被产品侧同样认真地遵守。

## B. 典型场景清单

每个场景：第一人称描述 → 用户手里剩什么残缺线索 → 现有闭环能否承接。

**S1 · 蓝色的那张**（感知）
"我想找一张专辑，封面是蓝色的，好像右下角有个人影。"
线索：封面主色调/构图 + 模糊风格与年份。
缺口：无颜色/视觉特征筛选；筛选结果若以文字列表呈现，感知记忆完全用不上。（这是文档 5.3 自己举的例子，目前无承接。）

**S2 · 大一那年冬天**（情境）
"大一那年冬天天天听的那张，谁来着？"
线索：听取时期（人生阶段）+ 场景（宿舍）。
缺口：Find 没有"听的时期"轴（listenedAt）；用户极易把听取时期错当成发行年份；补记录场景下 addedAt 全部失真。

**S3 · 深夜的那种闷闷的电子**（感知+情绪）
"很闷、很重的低音，适合半夜戴耳机的那种。我说不出 genre。"
线索：声音质感/氛围；听的时间多半在深夜。
缺口：无声音/氛围轴（Tag 可承载但依赖当时打标）；添加时间的时段信息（深夜）目前被完全丢弃。

**S4 · 失恋那阵子**（情绪）
"分手那两个月单曲循环的专辑，想回去看一眼。"
线索：情绪 + 时期；也许当时在 Note/Tag 里写过。
缺口：情绪记忆只能靠 Tag 承载；Note 不可搜索；没有"回到那段时间"的浏览方式。

**S5 · 确定收藏过，但想不起来**（再认机制）
"我肯定收藏过这张，艺术家和名字都想不起来了。"
线索："收藏过"这个事实 + 模糊的感知印象。
缺口：文档已正确覆盖（渐进筛选），但缺"把候选缩到一屏封面以内"的体验设计，以及候选集内的打乱——再认需要看到封面，且候选集必须足够小。

**S6 · 只记得一个词**（感知-语言）
"名字里好像有个'海'字……或者是我当时写过'海边'？"
线索：一个字/一个词，可能出现在标题、艺术家、自己的 Note 或 Tag 里。
缺口：若 Collection 内搜索只覆盖标题/艺术家，用户自己写下的 Note 线索就浪费了。

**S7 · 咖啡馆的旋律**（情境-外部线索触发）
"刚才店里放了一段，我好像收藏过这张，是不是？"
线索：即时产生的模糊印象，需要快速验证"我有没有"。
缺口：搜索作为一级能力要快到"10 秒内确认"。这更多是对 Find 的验收标准而非新功能，但值得写进验收场景。

**S8 · 我为什么收了它？**（情境/情绪）
"三年前收藏的，完全想不起为什么。"
线索：无（记忆已蒸发），唯一可能的载体是当时的记录。
缺口：记录时若无任何"当时"的线索（一句 Note、听取时间），详情页就只有公共元数据——"我的"那一半缺失。这是编码缺口，不是检索缺口。

**S9 · 年底想回看这一年**（情绪+情境）
"12 月了，想看看这一年我留下了什么、最爱哪几张。"
线索：时间锚点（年末）。
缺口：Topster 存在，但没有"某一年"的天然入口；Review 无触发机制，全靠用户自发想起来。

**S10 · 都忘了收藏过**（情绪-重遇）
"这是我收的？都忘了，听两首……真好。"
线索：无主动线索，需要"被重新遇见"。
缺口：无任何重遇机制；Collection 默认 Recently Added 排序，老记录沉底即等于遗忘。

覆盖检查：感知 S1/S3/S6，情境 S2/S7/S8，情绪 S4/S9/S10，机制性场景 S5。三种记忆类型各有落点。

## C. 我的产品理念

> **Musicgraphy 不是一个专辑收藏列表，而是一座"线索库"：记录时以最低成本埋下未来的找回线索（时间、一句"当时"、一个词）；找回时让任何一根残缺线索都能把用户缩小到"一屏封面以内"，用再认完成回忆做不到的事。**

一句话版本：**记录是为了将来认出来，不是为了现在填完整。**

## D. 方案清单

### D0 三条设计原则（先于功能）

1. **再认优先（recognition-first）**：所有 Find 的结果一律以封面墙呈现，不以文字列表呈现；每一步筛选都要"看得见封面"。残缺记忆靠认出，不靠想起。
2. **一屏原则**：筛选的体验目标是"候选集缩小到一屏以内"（约 20–40 张封面），界面实时告诉用户"还剩 N 张"，让缩小过程可感知。
3. **编码即资产**：记录时每多留 1 比特"当时"（听取时间/一句话），都是未来 Find 的资产；但必须 opt-in 且 ≤2 次点击，不得违反 5.1 的低成本原则。

### D1 P0 必须做

**P0-1 Find 增加"听的时期"轴，与"发行年份"并列且明确区分**
- 对应场景：S2（大一那年冬天）、S4（失恋那阵子）、S9
- 服务目标：Find（第一优先）
- 推理链：数据模型已有 listenedAt/addedAt（AGENTS.md §4 用户数据），这是纯查询能力，零新数据；文档 5.3 第一个例子"2010 年左右"在用户心智中更常指"我听的时期"；情境记忆是三种记忆中最难被公共元数据覆盖的一类，而时间是系统唯一免费拥有的情境维度。UI 上用两个明确命名的字段（"发行年份 / 我听的时期"）防止混淆。成本：筛选面板一组区间控件。

**P0-2 Collection 内搜索覆盖 Note 与 Tag 全文（片段匹配）**
- 对应场景：S6（只记得一个词）、S8（我为什么收了它）、S4
- 服务目标：Find
- 推理链：Note 是产品里密度最高的私人线索载体，当前不可搜索等于"记忆已写下、未接线"；用户的残缺线索常是一个词，可能落在标题/艺术家/Note/Tag 任一处，搜索应当一处输入、多字段命中。技术上普通查询+索引即可（AGENTS.md §11 优先简单），不需要搜索集群。MVP 已有"Collection 内搜索"条目，此条是把它做对，不是新增功能。

**P0-3 搜索与筛选结果一律封面墙呈现 + 结果内"打乱"**
- 对应场景：S1（蓝色的那张）、S5（确定收藏过）、S10
- 服务目标：Find
- 推理链：再认优于回忆——文字列表强迫用户回忆，封面墙调用感知记忆；打乱（shuffle）打破 Recently Added 固定排序对老记录的掩埋，让候选集以随机顺序被再认。AGENTS.md §6 已定 cover-first，此条是把 cover-first 从 Collection 页贯彻到 Find 全链路。成本几乎为零（呈现层）。

**P0-4 记录时可选的"当时"微上下文：快捷听取时间 + 一句话**
- 对应场景：S2（补记录时期失真）、S8（我为什么收了它）
- 服务目标：Record（编码质量），反哺 Find
- 推理链：提取失败多数是编码失败。添加成功后给一次"闪过的机会"——"大概什么时候听的？"（默认"刚刚"，可一键选今年/去年/更早/某年）与"留一句'当时'？"（可跳过）。两个入口均 ≤2 次点击且可完全忽略，不违反 5.1；换来的是三年后"听的时期"轴（S2）与"为什么"线索（S8）的可用性。补记录（批量补记旧爱）是真实高频行为，不采集听取时间会让时间线从第一天起失真。

**P0-5 专辑详情页"记忆条"**
- 对应场景：S8（我为什么收了它）、S4（失恋那阵子）
- 服务目标：Find 的终点 + Review 的起点
- 推理链：找回的完成不是"定位到专辑"，而是"想起它对我是谁"。当前详情页以外部元数据为主，"我的那一半"（记录时间/听取时间/Tags/Note）散落或弱化。把既有字段组成一条第一人称记忆条（"你于 2023 年 8 月记录 · 听的时期：2023 夏 · Tags：夏天/海边 · 当时：青旅的天台"）。零新数据，纯展示重组。

### D2 P1 应该做

**P1-1 封面主色调/颜色筛选**
- 场景 S1 → Find。文档 5.3 自己举了"封面好像是蓝色的"，却没有承接；封面主色是离线一次性计算+缓存，成本可控。这是"文档的承诺，未兑现"清单里最具体的一条。UI 上以一排色块出现，不新增概念（它是筛选轴的一种）。

**P1-2 "重听"标记（更新最近重听时间）+ "最近重听"排序**
- 场景 S4、S10 → Review/Find。文档 5.5 明确列了"某一阶段反复听过什么"，当前无机制。一次"重听"点击=更新时间字段，为"反复听"积累最便宜的行为数据，也让"我最近重新听过什么"成为 Review 的入口。不引入评分（遵守 AGENTS.md §8）。

**P1-3 "手记"视图：自己的 Note 按时间排成的第一人称流（带封面）**
- 场景 S4、S9 → Review。把 Note 从详情页字段升级为回顾媒介——读自己三年前写下的话，是个人档案里情绪浓度最高的回顾方式，也是 5.8 "重新被理解"最直接的实现。零新数据，是 View（观察 Collection）而非新系统，符合 5.5 架构立场。作为 Collection 的一个视图入口而非顶级页面（AGENTS.md §13 页面边界），待核心闭环稳固后上。

**P1-4 筛选进度"还剩 N 张"与一屏目标**
- 场景 S5 → Find。把"渐进筛选"从理念变成可感知的界面反馈；用户始终知道离"一屏认出来"还有多远。成本极低，是 D0 原则 2 的落地。

**P1-5 "那年今日"轻卡片（单一卡片，不是 feed）**
- 场景 S10（重遇）、S9 → Review 触发。Review 缺的不是 View 而是触发时机；用 addedAt/listenedAt 的周年/整周做一张卡片放在 Collection 页，零新数据。刻意克制：只有一张卡片，不做算法推送（见 E），不打扰。

### D3 P2 可探索

**P2-1 时段自动情境标记（深夜/清晨）**
- 场景 S3 → Find。由添加时间推断时段，作为筛选面板里的"建议筛选"出现（如"深夜 (23)"），不作为新数据概念、不自动写 Tag。探索点：是否值得为一根新线索引入一个软概念；待 P0 验证后再评估。

**P2-2 年度回顾页**
- 场景 S9 → Review。年末是天然回顾时刻：某年新增/重听/最爱，可自动生成 Topster 式一页。约束：只用自有数据，不做营销式 Wrapped 的修辞；是 View 不是新系统。

**P2-3 记忆巡游（全库 shuffle 小样）**
- 场景 S10 → Review。从全 Collection 随机抽一小组封面供重遇，是玩具属性来源之一。探索点：与 P0-3 结果内打乱的边界，防止变成无目的刷封面。

**P2-4 发行形态筛选（现场专辑/EP/Live/重制版）**
- 场景 S3 变体（"那张现场专辑"）→ Find。外部元数据可提供，属于感知记忆中的"形态记忆"。优先级低：频率低于颜色。

### D4 目标延申支线（不是另起炉灶）

**支线一 · "时期"支线**：Record（listenedAt）→ Find 的"听的时期"筛选（P0-1）→ Timeline View（按听的年份分组）。
体现给用户的方式：筛选面板里"我听的时期"一项；未来 Collection 的按年分组视图。起点是文档 5.1 已有的"什么时候听过"，终点是 5.5 已写的 Timeline——支线两端都已在文档内，缺的只是中间接线。

**支线二 · "手记"支线**：Note → 可搜索（P0-2）→ 详情页记忆条（P0-5）→ 手记视图（P1-3）。
体现给用户的方式：搜索结果命中自己写过的话；详情页第一人称记忆条；"手记"视图。Note 从"可选字段"升格为产品最重要的记忆载体。

**支线三 · "再认"支线**：cover-first → 结果封面墙+打乱（P0-3）→ 颜色筛选（P1-1）→ 记忆巡游（P2-3）。
体现给用户的方式：找回全程"看得见封面"；一排色块筛选；随机重遇。把文档 5.3"封面好像是蓝色的"那句台词变成真正可用的能力。

**支线四 · "时刻"支线**：addedAt/listenedAt → 那年今日卡片（P1-5）→ 年度回顾页（P2-2）。
体现给用户的方式：Collection 页一张周年卡片；年末一页自动回顾。给 Review 补上它现在缺的东西：触发时机。

## E. 明确不做清单

1. **不做哼唱/音频旋律搜索**：S7 场景用"词片段+封面再认"承接大半；音频识别的技术复杂度与"非流媒体、非识别引擎"的定位（AGENTS.md §2）冲突，且失败成本（搜不到）极高。
2. **不做 AI 情绪识别/自动情绪标注**：情绪记忆是用户的私有语言，系统替用户标注情绪等于制造错误记忆；S4 由 Tag+Note+"听的时期"组合承接。
3. **不做推荐式"猜你想重温"、不做遗忘曲线排程推送**：把 Review 交给算法 feed 会破坏"Collection 是事实"的原则，让"档案"滑向"内容流"。重遇一律用确定性时间锚（周年）与用户主动 shuffle 实现。
4. **不做结构化情境字段（地点/人物下拉框等）**：情境记忆是叙述性的，强结构化会抬高记录成本且远不如一句 Note 能装；若未来做地点，必须可选且低摩擦。
5. **不做评分体系**：与 AGENTS.md §8 一致；"重要程度"由 Favorite+Tag+重听行为表达，除非未来能证明评分带来明确找回价值。
6. **不做记忆社交化（分享手记/回忆卡给他人）**：第一人称记忆的价值恰恰在于私密；社交化会把产品拖向社区定位，明确越界。
7. **不做"记忆图谱"类关联可视化**：看起来很酷，但对应不出一个具体的找回场景，违反 5.7"不因看起来很酷而进入核心产品"。

## F. 推理过程总览

1. **从记忆类型学出发**：人的音乐记忆分三类——感知（封面颜色/声音质感/一个词）、情境（时期/地点/场景）、情绪（深夜/失恋/第一次的震动），外加一个机制性事实：再认远易于回忆。
2. **用这个框架审计目标文档**：文档对"语义残缺"（年份/风格）+ Tag 私人词汇覆盖良好（优点）；但发现三类缺口——(a) Find 能力清单与文档自己举的记忆例子脱节（颜色、听的时期、Note 均无承接）；(b) 只建模了主动查询，没有建模触发；(c) 编码侧（记录时埋线索）只有半句话。
3. **把缺口翻译成场景**（B 节 10 个），每个场景都追问"用户手里还剩什么线索、现有闭环接不接得住"。
4. **场景反推功能**：每条功能都指明哪个场景、哪个目标、为什么是现在、成本边界在哪（D 节推理链）。优先级服从 AGENTS.md 的 Find > Record > Organize > Review；P0 全部落在 Find 与 Record 的编码侧，且全部建立在既有数据（addedAt/listenedAt/note/tag/cover）之上——不引入新数据系统，与 5.7 低复杂度和"Collection 是事实"的架构立场一致。
5. **延申支线全部从文档内部已有名词生长出来**（listenedAt、Note、cover、addedAt），是"接线"而非"扩建"；明确不做清单守住"低复杂度"与"个人档案"两条底线，主动杀掉发散度更高的诱惑（音频搜索、AI 情绪、推荐式回顾、记忆图谱）。
