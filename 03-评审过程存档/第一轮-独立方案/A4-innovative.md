# A4 功能挖掘者 · 第一轮评审

> 人格声明：发散度 4/5，稳定度 2/5。我的职责是把团队的可能性空间撑大：新的记录触发、新的找回线索、Topster 之外的 View、玩具属性的新表达。每条主张都标注服务环节与论证强度；论证不出来的，我自己先把它降为 P2。

## A. 对现有产品目标的评价

### A1. 优点（3 条）

1. **四层闭环是所有新功能的"上诉法院"。** 对我这种爱挖功能的人来说，这套结构不是枷锁而是自由的保障：我知道在哪里可以疯（View 层、表达层），在哪里必须收敛（数据层、概念层）。"功能必须解释自己服务哪个环节"这条规则让发散有了裁判，这是文档最值钱的一句设计。
2. **"Collection 是事实，View 是观察"是全文最具生成力的一句话。** 它把表达力的边际成本降到接近零：任何新 View 都不需要新数据系统。这句话实际上是在邀请我——尽管挖 View，挖不坏产品。
3. **"外部元数据 vs 用户资产"的数据二分，暗中为一切个人化表达留了承重墙。** Genre/Tag 语义区分、用户数据不可覆盖，这两条让"个人档案"的情感核心在数据层就立住了，而不是靠 UI 装出来的。

### A2. 盲点（4 条）

1. **档案是哑的。** 全文没有任何"声音"的位置——没有试听、没有音频确认，封面是唯一被承认的视觉资产。这意味着产品的表达力上限 = 封面网格的表达力上限。对一个音乐档案来说，这是最隐蔽也最大的天花板。
2. **记录触发方式只有一个漏斗。** 目标一的美好承诺（"几秒完成记录"）被单一入口锁死：一切路径都汇入"打字搜索"。但听歌发生在外部场景（流媒体、黑胶、朋友车上、电台），产品没有在任何一个场景里放入口。记录成本的瓶颈不在表单，在"你得先想起要打开它"。
3. **Find 被建模为"字段查询"，但人的记忆是联想式、情境式的。** 目标文档自己举的四个记忆样例里，"封面好像是蓝色的"以现有目标方案根本做不到——目标举的例子超出了目标自己的方案。文档覆盖了属性记忆（Genre/Year/Tag），完全没覆盖联想记忆（"和 X 差不多同期听的那张""我加它那天还加了什么"）。
4. **Review 是纯拉动的。** 档案永远等用户上门，永远不会主动开口。但 Review 恰恰是闭环里唯一产出"继续记录的动机"的环节——它被当成服务的终点，其实它是 Record 的引擎。

### A3. 风险（3 条）

1. **"低复杂度"滑向"低表达力"。** 文档把概念数量当作唯一成本，没有算"情感收益"这一侧的账。一份功能全部及格、但情感上扁平的产品，玩具属性会无声死亡——不是被某个决定杀死的，是被一百次"这个先不做"杀死的。
2. **Tag 腐蚀风险。** AGENTS.md 明确禁止 Tag 变成复杂管理工具，方向正确；但三年不治理的个人词汇表（"夜晚/夜/late night"三兄弟）会反过来击穿优先级最高的 Find。禁止"管理工具化"不等于禁止"最轻量治理"。
3. **元数据源单点风险。** 搜不到的专辑（自印、Bandcamp 冷门、演出现场盘）按现有目标进不了档案，而个人档案里最珍贵的恰恰是这些。Record 承诺"凡听过的皆可记录"，却没有给漏斗破裂时留兜底。

## B. 我的产品理念（一句话）

> **Musicgraphy 2.0 应该是一座"会自己开口说话"的个人音乐档案馆：任何时刻 3 秒记下耳朵里的专辑，用"人想起一首歌的方式"（颜色、时节、联想、一句手写笔记）把它找回，并在你想不起来去找它之前，先让它浮出水面。**

三个动词定义这条理念：**记下（追着听歌场景走）→ 找回（追着记忆方式走）→ 浮出（不等用户上门）。**

## C. 方案清单

标注说明：每条前的【】为维度标签（功能挖掘 / 创新型 / 支线）；每条给出 服务环节 → 推理链 → 论证强度。论证强度为"弱"或"中偏弱"的主张一律只放 P2。

### C.1 P0 必须做（6 条）

1. **【功能挖掘】渐进式筛选舱（多线索叠加 + 实时剩余计数）** — 服务环节：Find
   - 推理链：目标 5.3 明确要求"从多个已知信息逐步缩小范围"，AGENTS.md 搜索原则要求"渐进式过滤"。把它做成一等的交互对象：用户堆叠线索芯片（Electronic + 2010s + 夜晚 + 蓝色封面），界面实时显示"还剩 12 张"。搜索从"附属功能"升为一级能力，正是本文档的原话。
   - 论证强度：**强**。
2. **【功能挖掘】Note 全文检索** — 服务环节：Find
   - 推理链：Note 是 MVP 四件套（favorite/tag/note/时间）中唯一一个"只写不读"的；而 Note 恰是最私人化的记忆线索（"note 里写过'鼓像心跳'的那张"）。找回价值极高、工程成本极低。
   - 论证强度：**强**。
3. **【功能挖掘】外链粘贴记录（Share-link capture）** — 服务环节：Record
   - 推理链：听歌发生在 Spotify/Apple Music/Bandcamp/YouTube 里，现有唯一入口要求用户切到 Musicgraphy 重新打几个关键词——记录成本的大头不是表单，是"换一个 App 再描述一遍"。粘贴一条链接 → 自动匹配专辑 → 确认，把记录成本从"几个关键词"降到"一次粘贴"。这是对目标一"几秒完成记录"最直接的兑现。
   - 论证强度：**强**。
4. **【功能挖掘】记录时顺手抽取封面主色调** — 服务环节：Find（数据基建）
   - 推理链：目标 5.3 自己举的例子"封面好像是蓝色的"，现有方案做不到。在添加瞬间用客户端 canvas 抽取主色存一个字段，成本一次性，为"颜色找封面"（P1 UI）铺好唯一的数据前提。数据在记录时顺手产生，不给用户任何新概念。
   - 论证强度：**强**（目标文档举的样例本身就是需求证明）。
5. **【功能挖掘】重复记录语义 = "又听了一次"（数据模型早决定）** — 服务环节：Record + Organize + Review
   - 推理链：个人档案的核心事实不是"有没有这张"，而是"我什么时候听过"。重复添加不是错误而是事件——AGENTS.md 数据原则里 listenedAt 已经存在，说明模型本来就该容纳"收听史"。趁早决定，避免日后把"再次记录"当成 bug 修掉。
   - 论证强度：**强**。
6. **【功能挖掘】手动建卡兜底（无元数据也能进档案）** — 服务环节：Record
   - 推理链：AGENTS.md 说外部元数据"可以重新同步、修正或替换"——这句话暗示 Record 不应被数据源锁死。自印 CD、Bandcamp 冷门、演出现场盘恰恰是个人档案最珍贵的藏品，漏斗对它们失效 = 核心承诺对最需要的用户失效。允许手工输入标题/艺术家 + 占位封面，日后元数据补齐时自动回填（外部字段可替换原则在此兑现）。
   - 论证强度：**强**。

### C.2 P1 应该做（10 条）

1. **【功能挖掘】颜色找封面筛选器** — 服务环节：Find。推理链：P0-4 已存主色，此处只需一个色板筛选 UI；"我记得封面是蓝色的"是文档自己举的记忆场景，如今变成可点的线索。论证强度：**强**。
2. **【功能挖掘】联想式找回（"跟这张同期听的"/"同天添加的"/"同 Tag 的其他专辑"）** — 服务环节：Find。推理链：人脑回忆靠联想不靠字段（"和 X 差不多时候听的那张"）；所有线索均来自已有 Collection 数据（addedAt/tag/artist），零新数据、零新概念，却补上目标 5.3 完全没覆盖的联想记忆。论证强度：**强**。
3. **【功能挖掘】时间锚点筛选（"上周加的""去年夏天"）** — 服务环节：Find + Review。推理链：时间是人类记忆最强的索引之一，addedAt 数据已在；把绝对日期翻译成"时节/阶段"的自然语言切片。论证强度：**中偏强**。
4. **【创新型】Topster 图片导出（比例/背景/标题自定义）** — 服务环节：Review。推理链：Topster 玩具价值一半在"做出来"，另一半在"带走"——无导出则 5.6 目标的表达闭环断在最后一厘米。导出不是社交功能，是"表达完成"这个动作本身。论证强度：**强**。
5. **【创新型】30 秒试听（点击封面出声）** — 服务环节：Find（确认"是不是这张"）+ Review。推理链：音乐档案不应该是哑的——找回的最后一公里最终要靠耳朵确认；若外部预览音源不可得则自动降 P2。论证强度：**强**（依赖音源可得性）。
6. **【功能挖掘】Tag 轻治理三件套（重命名 / 合并 / 最近使用自动补全）** — 服务环节：Organize → 保护 Find。推理链：AGENTS.md 本就预留了"最近使用、自动补全"；三年不治理的词汇表会击穿最高优先级的 Find。治理不是"分类管理工具"，是 Find 的防腐剂。论证强度：**强**。
7. **【功能挖掘】批量操作（批量打 Tag / 批量 Favorite）** — 服务环节：Organize。推理链：目标二要求 Collection 在几千张规模下"分类效率"可用，单张操作在千张规模下线性失效。论证强度：**强**。
8. **【支线】收听日记（Timeline 按记录时间 + 详情页"我的收听史"时间条）** — 服务环节：Review + Record。推理链：数据原则里 listenedAt 已存在；"档案"与"日记"一线之隔，补上它让 Review 从"浏览藏品"变"重温经历"。体现给用户的方式：专辑详情页多一条小时间线；Timeline View 可切换"按记录时间"。论证强度：**中偏强**。
9. **【创新型】回忆翻牌（每天/每周一张牌，翻开是老专辑 + 你当年写的 Note）** — 服务环节：Review + Find。推理链：Review 是纯拉动的盲点；浮出机制用零新数据（随机 + Note）让档案开口。论证强度：**中**。
10. **【支线】数据导出/导入（JSON 全量备份）** — 服务环节：Record（长期信任）。推理链：AGENTS.md 说"用户数据必须被视为用户资产"——资产的定义包括可带走；敢投入记录的前提是相信档案不会消失。体现给用户的方式：设置里一个"导出我的档案"按钮。论证强度：**强**（工程上极便宜）。

### C.3 P2 可探索（8 条）

1. **【创新型】色环视图（Color Spectrum View）：全 Collection 封面按主色排成光谱墙。** 服务环节：Review + Find。推理链：与 P0-4/P1-1 共用同一份颜色索引——**检索线索与表达素材是同一份数据的两个用途**，这是"零新概念的玩具属性"的范本。论证强度：**中偏强**。
2. **【创新型】Tag 星座图（个人词汇表的可视化：词按数量成星，共享专辑的词相连）。** 服务环节：Review + Organize（重叠的词互为合并候选——同一张图既是回顾视图又是治理工具）。论证强度：**中**。
3. **【支线】档案重访仪式（"周日十分钟"全屏翻牌模式：重遇老专辑，顺手补 Tag/Note）。** 服务环节：Review + Organize。体现给用户的方式：首页一个入口按钮进入全屏模式，其余无新概念。推理链：把"整理欠账"变成玩具时间。论证强度：**中**。
4. **【支线】年度档案（Year Wrap：按年自动生成 Topster + 数据小结，可导出长图）。** 服务环节：Review。体现方式：每年 1 月首页出现"你的 2026"。推理链：Topster 的自然周期化，零新数据。论证强度：**中偏强**。
5. **【创新型】手绘封面替代（无元数据/无封面时允许上传或绘制占位封面）。** 服务环节：Record + Review。推理链：占位艺术本身会成为档案最有人味的部分。论证强度：**中**。
6. **【支线】只读分享链接（单个 View 的只读快照页，无评论无关注）。** 服务环节：Review。体现方式：任何 View 右上角"生成链接"。推理链：表达需要观众，但分享页不是社区——边界清晰。论证强度：**中**。
7. **【功能挖掘】浏览器书签小工具（bookmarklet：任意网页一键记录）。** 服务环节：Record。推理链：记录入口追着场景走的低成本实验。论证强度：**中偏弱**（依赖渠道、平台限制多）。
8. **【创新型】档案馆主题皮肤（季节/纸质/黑胶纹理）。** 服务环节：Review。论证强度：**弱**——按规则论证不出强贡献，只能垫底 P2，等核心做完再说。

## D. 明确不做清单

1. **推荐/Discovery 引擎**：任何"你可能喜欢"都在动摇"个人档案"的定位，AGENTS.md 边界明确，我举双手同意。
2. **社交关系（关注/评论/点赞/协作编辑）**：分享一个 View 是表达，建立关系是社区——只做前者。
3. **游戏化积分/成就系统（徽章、打卡、连击）**：玩具属性 ≠ gamification。档案的玩味来自"东西本身好看好玩"，不来自操作性条件反射。这可能是我和一般"玩具化"方案最想划清的一条线。
4. **统计 Dashboard（听歌时长报表、口味分析报告）**：把档案变回后台管理系统，AGENTS.md 第 12 条直接禁止。
5. **1–10 评分**：AGENTS.md 已说明理由，我补充一条——评分是公共评价体系的语言，会污染"Tag 是我的语言"这条产品人格。
6. **对话式 AI 检索助手（"跟 AI 聊天找专辑"）**：看似服务 Find，实则与"渐进式缩小、过程可见"的找回哲学冲突——用户要看见自己的线索堆叠，不是要一个黑箱答案。AI 只允许躲在幕后做外链→专辑实体的匹配（P0-3 的实现细节）。
7. **Last.fm 等被动全量导入**：被动导入把"档案"变成"日志"——记录这个动作本身就是记忆仪式，取消仪式等于取消产品人格。（技术同步能力可作为未来匹配器的底层，但不作为用户叙事。）
8. **Discogs 式版本/压制/市值管理**：不解释。

## E. 推理过程总览

1. **从文档自己的例子往回挖。** 目标 5.3 举了四个记忆样例，其中"封面好像是蓝色的"以现有方案做不到——文档举的例子超出文档自己的方案，这是最硬的缺口，所以颜色线索进 P0（先存数据）+ P1（再上 UI）。
2. **从数据原则里捡便宜。** listenedAt 已存在 → 收听日记；"用户数据是资产" → 数据导出；"元数据可替换" → 手动建卡兜底。很多"新功能"其实是文档已有原则没长出的器官。
3. **找闭环里最薄弱的环。** Review 是纯拉动、Record 是单一漏斗——两个薄弱点恰好分别催生"浮出机制"和"多入口记录"，它们构成我理念的两个动词。
4. **双用途原则控复杂度。** 每份新数据尽量两个用途：颜色既是 Find 线索又是 View 素材；Tag 星座既是回顾视图又是治理工具。这是"低复杂度"与"高表达力"同时成立的唯一合法通道——不是少挖功能，而是让每个功能干两份活。
5. **降级纪律。** 所有论证强度为弱的（主题皮肤）、依赖外部条件的（bookmarklet、试听），自动沉 P2；所有引入新概念的（对话式 AI、gamification），直接进不做清单。发散的部分交给 P2 和支线，P0 只留六条闭环承重墙。
