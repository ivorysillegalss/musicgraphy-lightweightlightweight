## 2. 反驳（反对谁的什么主张，理由）

### 反驳一：A5 把 Review 层主张顶进 P0（P0-2"一年前的今天"、P0-3 Topster 策展语义），以及重新解释"不是推荐引擎"围栏的提案

- **反驳理由一：违反 AGENTS.md §16 的优先级序。** §16 写明 `Find → Record → Organize → Review → Discover`，且"任何新功能如果削弱快速记录或后续找回能力，应谨慎接受"。策展语义（副标题+自定义顺序）与时间回响入口服务的都是 Review，不加强 Record/Find 任何一环。P0 门禁是我第一轮方案的全部骨架，若 Review 项可进 P0，门禁即失效——今天让进两个，明天就有第三个。补一个工程事实：回响入口是条件触发的空功能，档案建立的第一年里"去年今天"永远为空，把它放 P0 等于为整个早期生命周期建造一个不能点火的功能。
- **反驳理由二："十年后无法复原的历史事实"是在用假想的未来收益购买今天的优先级。** 这是 5.7"不因看起来很酷而进入核心产品"的时间维度版本：以一个十年尺度的叙事为 P0 立项，等于让不可验收的远期价值压过可验收的近期承诺。策展语义还引入真实的当期成本——副标题与自定义顺序是必须持久化的 View 状态，正是 AGENTS.md §9"避免产生第二套状态"要防的东西的最小形态，但再小也是第二套。
- **反驳理由三：围栏重释会开启先例。** A5 对"回响"的论证本身是自洽的（只自我引用、不引外部语义），其最小工程形态也确实只是一个 addedAt 区间查询。我反对的不是这个查询，而是**把"重新解释围栏"本身变成一个可复用的论证模式**：一旦接受"禁令的真实含义可以重新划定"，此后每一次功能评审都会有人援引先例。"档案开口"的最小形态无害，但它的存在会成为通往通知、推送、engagement 机制的台阶——那时反对的就是推荐引擎的下一次形态。判定：回响入口与策展语义均归 P2，各自独立裁决，与我对 Topster、当年今日的第一轮裁决完全一致。A5 自己也承认这些是"给汇总的原料而非工单"——我按原料处理，不予立项。
- **补充**：A5 的观察池方法（先让用户自然语言积累证据密度，再决定系统结构）是全篇最有价值的部分，我全盘采纳——这正是档案管理员能接受的唯一一种"未来主义"：用信号决定立项，不用愿景决定优先级。

### 反驳二：A4-P0-5"重复记录 = 又听了一次"的收听事件日志模型

- **反驳理由一：引入第二类数据对象。** 收听史意味着"事件"成为与 Collection Record 并列的数据对象，这与 AGENTS.md §4 的模型相悖——该节明确把 listenedAt 列为 Collection Record 上的一个用户字段（单数），推荐关系是 `Album Metadata 1 --- N Collection Record`，不是 `Album 1 --- N Listen Event`。§4 还说"数据库模型应优先围绕 Collection Record 建立"。
- **反驳理由二：事件日志把去重成本转嫁给每一个 View。** Collection 网格、筛选计数、Topster、Timeline 全都默认"一专辑一条"；事件模型下每个 View 都要做聚合并决定聚合规则（哪次收听代表这张专辑？）。这是用数据层的灵活换取所有展示层的永久复杂度，方向与 §11"优先简单"相反。它还破坏"是否已收藏"的布尔判断（§6）——我的 P0-3 已收藏标注与添加拦截都建立在这个前提上。
- **反驳理由三：需求本身真实，但已有更便宜的解。** "我又听了一遍这张"的正确表达是**更新 listenedAt**（A3-P1-2 的"重听"标记），零新对象、零聚合成本，且"某一阶段反复听过什么"（5.5）由此自然获得数据。
- **判定**：坚持一专辑一记录。A4"趁早决定数据模型"的呼吁我接受——但决定的内容恰好与 A4 相反：趁早决定**不建**事件日志，重复添加被防重复提示拦截（进 P0-1），重听以更新 listenedAt 表达（P1）。

### 次要保留意见（不展开正式反驳）

- **A4-P1-5 30 秒试听**：音源依赖脆弱（A4 自认可降 P2），且"点封面出声"向播放器形态漂移；确认需求已被封面墙再认 + 外链跳转覆盖。进不做/观察。
- **A4-P0-6 手动建卡兜底**：需求真实（自印、冷门藏品），但频率低且重新引入了 5.1 刚消灭的表单成本。P2 观察池，观察信号：真实用户搜索无结果的次数。
- **A4-P1-7 批量操作**：与我第一轮不做清单第 16 条冲突，维持原判——千张级痛点才值得引入多选 UI 与误操作风险，观察信号：Tag 补全后单张打标时长是否仍构成瓶颈。

## 4. 最终产品主张（200-400字定稿）

> Musicgraphy 2.0 是一座先保证"每一条都找得回来"、再谈"好看好听"的个人专辑档案。它只做两件难事。一是把"搜索→确认→添加"压到三步、输入五秒以内：候选零输入、可粘贴识别、已收藏当场可见；Favorite、Tag、Note、听的时期全部是确认层上的可选项而非义务。二是把"模糊找回"做成试错式筛选：Genre、发行年份、我听的时期、Favorite、Tag、Note 片段全部可叠加、实时报数、永远以封面墙呈现，让任何一根残缺线索都能把候选缩到一屏之内。数据上恪守三条铁律：外部元数据与用户记录分离；一专辑一记录，重听只更新时间；每一条用户数据可导出带走。View（Topster、Timeline）永远只是观察方式，不进主干、不产生第二套状态；推荐、社交、评分、自动同步、统计、试听一律不做。记录时埋下的每一根线索都是三年后的找回资产——档案的价值不在功能列表的长度，而在十年后翻回去时，每一条都还在、都认得出、都带得走。

（约 330 字）

## 5. 优先级变化

### 升级（4 项）

1. **listenedAt 语义确定：P1 → P0。** 变更依据：第一轮我给 P1 的理由是"Review 层尚未启用"；A3 证明它同时是 Find 第一优先的接线前提（"听的时期"轴），A4 证明补记录场景会让 addedAt 从第一天起失真。数据模型决策先于数据积累，且语义确定是一句话的决定，不是功能。
2. **"听的时期"筛选轴：并入 P0-2（四维 → 五维）。** 依据：与第 3 条完全对称的建设窗口裁决——筛选器正在 P0-2 建造，接入既有 listenedAt 字段的第五个维度边际成本≈0，事后补轴要二次动工整个筛选 UI；且 5.3 文档自己的第一个记忆例子就是听的时期记忆。约束：与发行年份明确分开命名，只读既有字段，不引入时间管理功能。
3. **Collection 内搜索覆盖面：P0-3 内容扩充。** 从"标题/艺术家"扩为"标题/艺术家/Tag/Note 片段"。依据：A2/A3/A4 三方收敛 + 5.3 自举例子的承接；普通 LIKE 查询在个人规模下即可（A2 的工程判断），不引入搜索集群，符合 §11。
4. **防重复提示：P1 → 并入 P0-1 确认步。** A2 的"已收藏前置标记"证明它本来就是添加路径的一段而非独立防线；A4 的呼吁反证了"趁早决定"的价值——决定的内容是不建事件日志、添加时拦截重复。

### 新增进 P1（3 项）
