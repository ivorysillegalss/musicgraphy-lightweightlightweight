## ② 减量方案提案（两档供勾选；top-N 值均为**固定值不随库存漂移**）

### 2.0 共同机制（两档同构，仅 N 值与范围不同）

- **切片点 = 渲染层**（`cabinSection` 内，见 §③）：每轴取 top-N 生成可见 chips；
  **剩余项进「更多」收纳**；激活值强制保全（当前选中的 chip 无论是否进 top-N 必然可见，
  复用 facetChips 既有 `count>0 || activeValue` 保全语义，切片在其后叠加）。
- **「更多」入口形态 = 舱内嵌套 `<details>`**（`<summary>更多 N 项</summary>` 同轴内联，
  原生零 JS 零新 URL 参数，与 S2-31 原生 details 先例同族）。备选形态否决理由：
  `?full=1` 类展开参数 = 新 URL 参数 + saved-views query_json 三处联动（S2-31 已否决
  年份区间的同款理由）；独立筛选页 = 为单次需求建页，违产品工程原则。
- **countAxes 零改动**（R-114 需求红线明文「countAxes 计数与轴排除语义不动」）：切片只动
  渲染数组，全量 facet 仍服务端计算（FR-2 计数语义、countTotal 求和、active 保全全部原样）。
- **chips = `<a href="?…">` 语义零改动**：buildHref/parseFilter/参数集（q/genre/year/period/
  fav/tag/color/cursor）一字不动；切片只减少 `<a>` 元素个数，不增不改名。

## ③ 实现影响面

### 3.1 切片位置：渲染层（推荐）vs 服务端

- **渲染层切片（推荐）**：`cabinSection`（pages/collection.ts:93）是 SSR GET / 与
  /fragment/cabin（pages.ts:209-217）的**唯一渲染汇合点**——在函数内对
  `counts?.genre/year/tag` 做「active 保全 + top-N + 其余进嵌套 details」，两通道自动一致，
  单点实现零漂移。年份若选 count DESC 口径，在渲染层对切片副本排序（`[...facets].sort`），
  **SQL 零改动**（AXIS_SQL.year 保持 year DESC——改 SQL ORDER BY 会动 countAxes 输出语义，
  触碰红线边界，不值）。
- **服务端切片（否决）**：在 routes/pages.ts GET / 处切片则 /fragment/cabin 须同步复制逻辑
  → 双点实现漂移风险；且 countAxes 本身不应加 slice 参数（红线明文「countAxes 不动」）。
- **取数面零变化**：countAxes 仍全量 facet（76 项年份的 GROUP BY 行数对 SQLite 是零负担
  量级，实测同类计数 <10ms）；列表 listPage LIMIT 改小 = 数据面只减不增。
- **DOM 诚实注记**：切片不减少 DOM 节点总量（「更多」details 内仍是全量 chips，无 JS 同权
  必须随文档直出）——本需求目标是**视觉密度**不是 DOM 规模；若未来要 DOM 减量需
  /fragment 按轴懒加载评审案，本文不建议。

### 3.2 墙实现面

- **常量拆分**：`PAGE_LIMIT` 拆 `WALL_LIMIT`（/ 与 /fragment/wall 用）+ /crate 保留 60
  （或用户裁全局 36/30）。listPage 既有 limit 参数直接接受，DAO/SQL 零改动。
- **岛屿**：wall-scroll.ts `AUTO_APPEND_MAX` 改值或加手动优先开关（autoLeft=0 → armNext
  直接不布防 IO，点击链路原样）；MutationObserver 重置逻辑不变。
- **测试影响（check 273/273 顺延）**：wall-scroll.smoke 现断言「自动 3 页后转手动」
  （S2-30 evidence ②）与 cabinSection 纯函数断言「恰好三轴收纳 + summary『75 项』」
  （S2-31 evidence ①）——N 值/收纳轴数变化须同步改写断言后全量复跑。

### 3.3 DD3 红线核对（chips 语义与 URL 参数不变——减量只是展示层）

- chips 仍是 `<a href="buildHref(...)">`，**零新参数、零改名、零状态迁移**：切片前后的
  href 集合是同一集合的子集关系；激活 chip 保全保证「当前 URL 状态在 UI 上永远可反选」
  （否则会出现 URL 带 genre=X 但 UI 无该 chip 的死状态——切片实现必须内置此保证，
  列为验收断言）。
- 嵌套 details 开合**不入 URL**（纯呈现态）：舱岛 swap 后「更多」回到收起——与 S2-31
  轴开合在 swap 后按激活态重算的行为一致，属可接受语义（§⑥-6 复核）。
- 墙 cursor 分页链路零改动（服务端顺链、data-next 透传、has_next 语义不变）。

### 3.4 S2-31 的配合（收纳体系内的增量）

- 轻量档复用 foldAxis 形态给 Tag 轴（第三轴转收纳）；「更多」嵌套 details 是 foldAxis
  chip-list 内的**新增内联组件**（新 CSS 类 ~0.3KB，summary 复用 axis-meta 摘要样式）。
- 激进档把 Genre 改 `open: f.genre !== null`（服务端置位逻辑与年份/听期完全同构，
  collection.ts:157-159 一行改）。
- 年份轴双层结构（top-N 可见 + 全量 details）与既有 180px 限高叠加时，建议「更多」
  内部继承限高（避免三层滚动嵌套）。

## ⑤ 与 R-115 入口带联算（结论）

沿用 R-115 件 §3.2 静态推算锚点（1080p 可视 940px；「到墙顶」= 页头下至墙第一行）：

| 情景 | 到墙顶估算 | 1080p 首屏可见墙 |
|---|---|---|
| 现状 + R-113（字体放大后，未减量） | ≈680-840 | 第 1 行（部分情景切顶） |
| R-113 + 乙入口带（+65）+ **R-114 甲档（-100~130）** | **≈615-805** | **第 1 行全 + 第 2 行大部** |
| R-113 + 甲入口带（+190）+ **R-114 甲档** | ≈740-930 | 第 1 行贴线/部分切顶——**甲入口带配甲档不稳** |
| R-113 + 甲入口带（+190）+ **R-114 乙档（-160~260）** | **≈610-870** | **第 1 行全可见** |

**结论**：
1. **轻量档（甲）足以容纳 R-115 乙方案（胶囊行 +65px）**：减量释放的 100-130px 完全覆盖
   入口带 65px 且净剩 ~35-65px 给墙第 2 行——两卡可同批交付，R-115 件「乙可独立先行」
   的结论在本档下升级为「乙 + R-114 甲可同批」。
2. **R-115 甲方案（探索卡组 +190px）必须配 R-114 激进档（乙）**，否则墙第 1 行在
   1080p 贴线/切顶——与 R-115 件「甲必须联动 R-114」结论一致，本件给出配比：
   **甲入口带 ⇒ 乙档舱减量**；**乙入口带 ⇒ 甲档即够**。
3. **墙张数减量（60→36/24）不改变「到墙顶」**（舱在墙上方）——墙减量的收益在
   首屏外深度（1,460→876/583px）与 SSR 字节，与入口带联算无关，可独立裁决。
4. 全部为静态推算；实施批以 devtools/IAB 实测复校（R-113 字号定稿后 chip 行高可能
   从 44px 上浮，届时按新行高重算行数）。
