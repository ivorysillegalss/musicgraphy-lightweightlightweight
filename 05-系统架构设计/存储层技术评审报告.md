## 0. TL;DR 裁决

**存储层架构不需要结构性改动，维持 C1（SQLite 本体 / node:sqlite 主选 / 单文件 / 手写 DAO）不变。**

理由：envelope 数字（DB 18.3MB、写并发 1、Note 扫描 1.5MB、单用户）与四条硬需求的组合，把 SQLite 嵌入式形态锁死为唯一合理解；本次评审未发现任何需求、规模或演进路径会推翻该选择。**但评审发现 10 项问题（R1–R10）**：2 项 P1（备份触发机制缺陷、mmap 与内存预算冲突）、6 项 P2（文档/规范一致性缺口）、2 项 P3（实施注记）——全部是实现层与规范层修正，不触及架构形态，**已直接修订进既有文档**。

| 备份与恢复（DD4/ADR-006） | ⚠️ 机制修订（R1）：启动时备份 → 启动 + 每日定时 |

## 2. 存储层形态逐维评审

### 2.1 引擎选型：SQLite 本体（node:sqlite 主 + better-sqlite3 回退）— ✅ 维持

- 复核算术确认：18.3MB（现）/ 36.6MB（上界）距 SQLite 甜区上限差 3 个数量级；写并发 = 1 使 WAL 单写者 + Node 单线程成为**零锁竞争、零连接池**的最简解。
- 一行否决清单（Postgres/Redis/ES/MQ/IndexedDB/重型 ORM）经逐项复核**全部成立**：每项否决都有 envelope 数字或硬需求编号支撑，非偏好判断。
- F2 风险处置正确：DAO 单文件隔离 + C2 一日回退，且唯一可证伪点收敛到 D2 spike——这是教科书式的风险收敛。
- **结论：不动。** §5 压力测试亦确认多用户/云备份/语料增长三个方向均无需换引擎。

### 2.2 进程内嵌入形态与连接模型（单连接 / 同步 API / 无池）— ✅ 维持

- 单用户 + 同步 API 意味着查询天然**串行化**：不存在 torn read、不存在事务竞态，`/api/export` 读到的永远是完整一致状态——这是该形态常被忽略的正收益，值得在实现时明确依赖而非绕开。
- 同步阻塞事件 上限可控：单查询 <1ms、LIKE 全扫 <5ms、导出构建 JSON 数十 ms 级——全部低于可感知阈值。
- **结论：不动。**

### 2.3 物理模式（分表 / 约束 / 索引）— ⚠️ 维持结构，补齐规范（R4/R5/R9）

- `album_metadata` 与 `collection_record` 物理分表 + `UNIQUE(user_id, album_id)` 物理约束：I1/I2 的执行权威选对了层级（数据库约束而非应用代码），**维持**。
- `UNIQUE(source, source_id)`、`(user_id, added_at DESC)` 等既有索引与查询模式匹配，5000 行规模全部毫秒级，**维持**。
- 发现并已补齐：`alias_sources` 列被 §5.2 引用但表定义缺失（R4）；`listened_at` 年份精度的存储格式未定死（R5）；两处次要索引缺失（R9）。详见 §4。

### 2.4 查询与检索策略（LIKE vs FTS5）— ⚠️ 维持策略，修正查询草稿（R3/R10）

- "现在 LIKE、FTS5 为 measured 升级路径"是正确的反过早优化决策：1.5MB 全扫 <5ms 已验证，FTS5 会引入触发器维护与分词复杂度，无当前收益。
- 但发现 **schema 与查询草稿不一致**：`genres` 是 JSON 数组列，§3 草稿却写 `GROUP BY genre`（无法执行）——已修正为 `json_each()` 展开（R3）。这是若不修正会在开工第一天就暴露的问题。
- 限制注记已补（R10）：SQLite `LIKE` 仅对 ASCII 折叠大小写，重音拉丁字母不折叠。

### 2.5 大对象处理（封面走文件系统，DB 只存路径）— ✅ 维持

`data/covers/` 磁盘缓存 + immutable 流式响应 + hash 命名 + F3 落盘兜底：BLOB 不进库是 SQLite 场景的正确实践，与 FR-5 首屏预算和 RSS 纪律②③自洽。**不动。**

### 2.6 迁移机制（SQL 文件 + PRAGMA user_version）— ✅ 维持（附一条实施注记）

- 单机单文件场景下，序号 SQL 文件 + `user_version` 是完备方案，引入迁移框架反而违背依赖预算。
- 实施注记：DDL 在 SQLite 中是事务性的，但 `journal_mode` 这类 PRAGMA 不能在事务内切换——迁移执行器须把连接级 PRAGMA 设置放在事务外。已记入 §6 验证清单。

### 2.7 备份与恢复（DD4 / ADR-006）— ⚠️ **机制修订（R1，本轮最重要发现）**

原设计"RPO=24h（**启动时**自动 `.backup()`）"存在缺陷：

1. **触发器与拓扑矛盾**：C1 是单进程长驻形态。进程若连续运行数月，则一次备份也不会发生——RPO=24h 的承诺在文档自己的部署拓扑下不成立。
2. **API 归属存疑**：`.backup()` 是 better-sqlite3 的 API；node:sqlite 截至 Node 24 未见稳定的等价 backup 方法——DD4 把回退驱动的 API 写成了主选方案的机制。
3. **"备份 = 复制一个文件"措辞误导**：WAL 活动期间数据库是 `.db + -wal + -shm` 三件套，直接复制 `.db` 会丢失 WAL 中未并回（checkpoint）的提交。

**已修订**（见 §4 R1）：触发 = 启动 + 每日定时（长驻进程内 `setInterval`/固定本地时间）+ 保留 7 份；机制 = `VACUUM INTO`（SQLite 3.27+ 内置，跨驱动等价，且产出紧凑快照）为主，D2 spike 验证 node:sqlite 是否已有 backup API；WAL 期禁直接复制；RTO<1h 不变；04A 云备份 Pro 路径不变（推的就是这份快照文件）。

### 2.8 持久化配置（PRAGMA 基线）— ⚠️ 修订（R2/R8）

- **R2（已修订）：移除 `mmap_size=134217728`。** 两个理由：① 库只有 18.3–36.6MB，远小于 128MB 窗口，mmap 收益≈0；② Windows 上内存映射文件的页计入进程工作集（RSS），而 RSS 分解表（"基线 45 + page cache 8 + 堆 15 + 余量"）**根本没有 mmap 项**——这是预算表与配置项的自相矛盾，威胁 RSS<100MB 目标的可信度。page cache 8MB 已足够。
- **R8（已修订）：补记 `synchronous=NORMAL` 的崩溃语义。** 精确表述：应用崩溃不丢数据（OS 已持有写入）；OS 断电/崩溃可能回滚最近若干提交（WAL 未 fsync 部分），由每日备份兜底。单用户写频下 `synchronous=FULL` 成本≈0，如需绝对持久可一键切换——决策已写入 ADR-001，不再是无记载的默认值。
- 实施注记（未改文档，进 §6 清单）：除 `journal_mode` 持久外，其余 PRAGMA 均 per-connection，必须在 DAO 打开例程统一执行；`foreign_keys=ON` 尤其容易被遗漏（SQLite 默认 OFF）。

### 2.9 数据主权出口（导出）— ⚠️ 补齐边界（R6）

I4/FR-6 承诺"导出可重建档案"，但 §5.4 的 JSON 导出**不含封面图片文件**：`cover_url` 是远端地址、`cover_local` 是本机路径——若远端失效（恰是 F1 场景），重建档案时封面全丢。数据主权承诺出现缺口。已修订 §5.4：导出提供"含封面 zip"选项（打包 `data/covers/`），I4 验收以含封面版本为准。

### 2.10 演进预留（user_id 列 / entitlements / saved_views / topster_views 声明位）— ✅ 维持

所有表保留 `user_id`（默认 `'local'`）、计费表只声明不建、Topster 策展模型同期才建：预留粒度恰当——既不因单用户砍掉关系维度（避免未来迁移数据），也不预建任何空表。**不动。**

| 需求/不变量 | 存储机制 | 审计 |
|---|---|---|

| I5 无打扰 | 架构中无通知子系统 | ✅ 覆盖（结构性保证） |
| FR-2 chips 实时计数 | 6 条索引查询 <1ms | ⚠️ R3 genre 计数草稿修正 |

## 5. 压力测试：什么信号才需要重开存储层决策

| 未来场景 | 当前架构是否扛得住 | 触发重评的信号 | 预期动作 |
|---|---|---|---|
| 多设备/多机同步 | ❌ 不支持（单文件单机） | 用户明确提出双设备使用 | 新增同步层（JSON 补丁 / last-win 合并）而非换引擎——SQLite 仍是正确的端点存储 |
| 多用户（≤10 活跃） | ✅ 基本扛得住 | 方案 A 后开放家庭/小团队 | WAL + busy_timeout 已具备；仅需应用层写队列，**无需 Postgres** |
| 语料超 5 万条 / LIKE >50ms | ✅ 有既定路径 | F4 阈值实测命中 | FTS5 升级（measured 路径，DAO 内部替换查询） |
| 04A 云备份 Pro | ✅ 零改动 | 方案 A 切换 | 快照文件定时推对象存储 |
| 数据量 10 倍（366MB） | ✅ 仍在 SQLite 甜区 | —— | 仅需上调 cache_size，其余不动 |

**结论：当前存储层在所有可预见演进方向上都没有死路；没有任何一条路径要求推翻 C1。**

## 6. D2 Spike 增补验证清单（随评审更新）

原 D2 只验证 node:sqlite + MusicBrainz 可用性，**增补以下五项**：

1. **backup API 探测**：node:sqlite 是否已提供 backup 能力；无则实测 `VACUUM INTO`（含 WAL 活动期执行）；
2. **PRAGMA 执行方式**：per-connection PRAGMA（synchronous/cache_size/foreign_keys/busy_timeout）在 node:sqlite 下的执行路径（`prepare().get()` vs `exec`），并固化进 DAO 打开例程；
3. **json_each 可用性与性能**：genre 计数查询（R3 修订版）实测 <5ms；
4. **迁移执行器**：DDL 事务包裹 + `journal_mode` 在事务外设置的实现验证；
5. **DAO 8 方法同形度**：与 better-sqlite3 逐方法比对（含返回值形状），确认"一日回退"承诺。

## 7. 最终裁决陈述

> 存储层的**形式选择**（嵌入式 SQLite 本体、单文件单机、单连接同步 API、手写 DAO、文件系统存 BLOB、SQL 文件迁移、JSON 导出）在当前与可预见的全部演进路径上均为最优或足够解——**不需要改动**。
> 需要（且已经）修正的是该形式下的**执行细节与文档一致性**：备份触发机制（R1）是唯一触及"承诺有效性"的缺陷，其余为规范补齐。所有修订已直接替换进 `DESIGN.md`、`design.json`、`07-ADR`、`02-数据模型` 四份文档，替换处均标注对应发现编号，可追溯至本报告。
