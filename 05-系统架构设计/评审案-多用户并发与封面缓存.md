## 1. 现状核实（2026-11-14 代码实况，全部主线仓 `musicgraphy/`）

### 1.1 三层并发分析

| 层 | 多人并发下的实况 | 结论 |
|---|---|---|
| 本站服务（页面/网格/本地检索/封面磁盘命中） | 单进程 Node + 同步 SQLite 读 1–2ms（perf-5000：可交互 34.4ms、HTML 70.3KB、RSS 78MB）；封面磁盘命中流式直通 | **不是瓶颈**，几百并发用户无压力 |
| 上游元数据搜索 | `src/server/server.ts:24-30` **一个 `MetadataRateLimiter` 实例喂全部四源**（MB/Deezer/iTunes/Discogs）→ 全局 30/min 为全部上游调用共享预算（iTunes 另有 20/min 子门 `sources.ts`）。突发 K 人同搜，第 K 个等约 K×1.05s，排队 >3s → 本地 429+Retry-After（`queue.ts`） | **真瓶颈**；但上游配额按客户端 IP/UA 计——多人部署**不增加**预算，只让争抢更早出现 |
| 封面下载 | `cover-routes.ts` 懒下载（`/covers/a/:albumId`）与 `onAlbumAdded` 钩子调 `downloadCover`（`covers.ts`）**完全绕开限流队列**（裸 fetch，15s 超时 / 5MB 上限 / 流式写盘） | 合规缺口 + 重复下载缺口 |

### 1.2 已到位、多人部署直接受益的既有设计（不动）

- **封面磁盘即共享缓存**：内容寻址 sha256 命名 + `Cache-Control: public, max-age=31536000, immutable`
  ——同一封面第二个用户起**零上游、零字节重传**（浏览器连条件请求都不发）。
- 流式写盘禁内存（纪律②）+ 5MB 上限 + `.part` 原子改名；并发首访竞态已幂等
  （`covers.ts` existsSync 命中丢临时件，写不坏）。
- **不做进程内图片缓存是刻意的**：OS page cache 在进程外不占 RSS，优于任何进程内 LRU。
- F1「搜索即快照」：每次搜索候选已落 `album_metadata`（`metadata/search.ts`）——
  本案 R1 的免费基础，缺的只是重复 q 仍打上游。
- 429+Retry-After 本地限流透传已实现（W1-2）。

## 2. 方案（R1–R4 = 最小集；R5 = 可选，登记不实现）

| # | 方案 | 改动点 | 预估 | 效果 |
|---|---|---|---|---|
| **R1** | **快照回放缓存**：内存 `q(规范化 trim+casefold) → album row ids` 映射，TTL ≈10min。命中 → 从 DB 重建 items（重算 `in_collection`），**零上游、内存 ~40KB**（只存 id 不存内容） | `metadata/search.ts` | ~25 行 | 重复/热点查询零上游；F1 快照本就落库，语义天然一致 |
| **R2** | **single-flight 查询合并**：同 q 并发到达共享同一次在途上游调用（`Map<q, Promise>`） | `metadata/search.ts` | ~15 行 | 多人同秒搜同一词 = 1 次上游 |
| **R3** | **封面下载收编**：① in-flight single-flight（同封面并发懒下载合并为一次 fetch）；② 统一「串行 ≥1s + 在途 ≤2」**独立门**（CAA/archive.org 无 30/min 硬规，**不占搜索 30/min 窗**）；`onAlbumAdded` 钩子与懒下载同走此门 | `metadata/covers.ts` + 新 gate 文件 + `server.ts` 接线 | ~35 行 | 合规缺口闭合；存量回填 5000 张 ≈ 88min 低峰一次性可跑 |
| **R4** | **回填空闲门**：批量回填任务仅在搜索队列/封面门空闲 >N 秒（建议 N=10s）时注入下一张；交互永远优先 | gate 文件内 | ~15 行 | 多人白天使用时批量回填不会吃光配额致全员 429 |
| **R5** | **跨源轮转扩预算（可选）**：四源拆独立 limiter 实例 + 全局仍串行 ≥1.05s；MB 窗满 → 直接轮转 Deezer/iTunes 而非排队 20s → 聚合预算 ~100+/min | `sources.ts` + `server.ts` | ~40 行 | **行为变更，仅 >100 用户规模才需要——登记不实现**（Q5） |

**冻结红线核对**：全局串行 ≥1s **保留不重开**（R1–R4 均不触碰；R5 也保持串行，仅改窗口归属）；
运行时依赖仍 = 2（全部手写零新包）；RSS 缓存预算 <0.5MB；DAO 不动（缓存放 metadata 域）；
无 JS 基线不动；落点 = 主线仓 `musicgraphy/`。

## 3. 容量量化

| 规模 | 搜索压力 | 判断 |
|---|---|---|
| ~50 人（峰值 2h 内 1000 次/天 ≈ 8/min，突发 ×3 = 24/min） | R1+R2 消化重复查询后，上游净调用显著低于名义值 | 现有 30/min 够用 |
| ~100+ 人 | 需 R5 轮转 | 届时另案追认 |
| 封面磁盘 | 5000 张 × ~60KB ≈ **300MB 量级**；可再生成（外部元数据）但重建需 ~88min 上游 | 是否纳入备份/归档口径见 Q4 |
