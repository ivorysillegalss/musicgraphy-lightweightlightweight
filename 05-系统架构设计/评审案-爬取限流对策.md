## Q1 · 503 墙的本质是什么？（定调）

**政策性速率墙，不是总量配额墙。** MB 官方 = 按 IP 平均 1 req/s、超速 100% 拒绝
（queue.ts:2 注释即此口径）。本项目自我防线（全局串行 1050ms + 30/min 滑窗，
queue.ts:31-32）本就低于官方线——夜窗 8h × 30/min = 理论 >14,000 次/夜余量，
而剩余缺口 ~66 行按 1.05s/次 ≈ **70 秒即可跑完**。三遇墙（pass2/pass3 + 2026-11-16
增量令受阻）的教训：**瓶颈在「遇墙即停」的对策缺失，不在额度**。1b74890
「对 IP 加剧」实况说明共享出口 IP 信誉是放大因子——这类墙靠退避与熔断穿越，
靠多源绕过，**不靠提额**。

## Q2 · 现状架构实况（对策的地基）

- 降级链 MusicBrainz→Deezer→iTunes→Discogs（server.ts:31-36，数组序即优先级）；
  **Deezer 本环境不可达**（api.deezer.com TCP 超时 ×2，34d4837 提交说明实测披露）
  → 实际有效链 = 3 源；**Discogs 无 token 未启用**（sources.ts:279 `enabled=token!==''`）。
- 全局限流器 queue.ts（1050ms 串行 + 30/min 滑窗 + 本地拒绝不占上游窗口）；
  iTunes 叠加 20/min 门（sources.ts:174）；封面走独立 CoverGate（不占搜索窗）；
  mb-calibrate CLI 用**独立 limiter 实例**（与服务进程不同享窗口）。
- MB 客户端**无自动重试**——503 抛 UpstreamError 透传 Retry-After（musicbrainz.ts:73-76）；
  退避重试只在 mb-calibrate CLI（单发：min(Retry-After,120s) 一次，二次 503 计 failed，
  mb-calibrate.ts:170-185）。**全链无指数退避、无连续失败熔断**。
- 字段映射逐源对比（AlbumCandidate）：

| 字段 | MB | Deezer | iTunes | Discogs |
|---|---|---|---|---|
| year | ✓ | ✓ | ✓ | ✓ |
| country | ✓ | 恒 null | 恒 null | ✓ |
| genres | 恒 []（搜索不带，须 +1~2 次 lookup） | 恒 []（API 有但映射未取） | ✓ 单值粗粒度 | ✓ genre+style 较全 |
| cover | CAA | ✓ | ✓ | ✓ |

  **结论**：MB 被墙时——year 可由 iTunes/Discogs 补；country 仅 Discogs（MB 可用时无需他源）；
  genres 是多源回退的真正增量价值（iTunes 粗 + Discogs 全，合并口径见 Q5）。

## Q3 · 六选项评估（推荐链在此节末尾）

### B1 字段级多源权威化回退（主案候选）
MB 503/未命中 → 按缺位字段向 iTunes/Discogs 查询，经既有 upsertAlbum 保守合并
（IM-12 非空才覆盖，writes.ts:41-69）+ alias_sources 归并（album-merge.ts:30-45）。
复用同一全局 limiter（零新限流通道）、零新依赖。风险 = 跨源 identity 归并靠
title+artist NOCASE 等值（album-merge.ts:37-43），同名异碟误归并须以
mb-calibrate 传行现值技巧（mb-calibrate.ts:209）防分裂 + 保守合并兜底。
工作量 M。红线 ✓ 全部。

### B2 用户自有 API key/token 池（BYO key）
逐源诚实结论：**Discogs 有 token**（文档口径认证 60/min vs 匿名 25/min，未实测；
代码已有单 token 槽位 config.ts:41 + 无 token 停用 sources.ts:279，扩多 token 轮换 = S）；
**Last.fm/Spotify 有 key 体系但本仓无该源**（引入 = 新增 Source 实现）；**MusicBrainz
无 key 体系——对 MB 本身完全不适用**（官方靠 UA 标识 + per-IP 限速；唯一合规杠杆 =
UA 内留有效联系方式）。与 R-112 多用户天然契合（凭据按用户加密存储 + per-user
limiter 分域，WeakMap per-chain 先例 search.ts:40-42），但**先有用户体系才有 BYO**
（现无 users 表，A6）。工作量：单源多 token = S；BYO 池 + 多用户绑定 = L。

### B3 调度优化（优先级最高的一项）
① **连续 503 熔断**（现状无——ca48ba5 记载 152 张级联 503 教训）：连续 N 次 503
即整批熔断停跑 + 退出码可判，杜绝级联撞墙；② 指数退避序列（现固定一次）；
③ 夜间批窗口（停服纪律已在脚本头注 mb-calibrate.ts:5；禁 PM2 红线 → 手跑/OS 计划）；
④ 批次计划持久化（现续跑 = 每次全量枚举从 DB 状态推导，mb-calibrate.ts:82,121-156）。
工作量：熔断+指数退避 = S；持久化 = M。零新上游、零隐私面变化。

### B4 出口 IP 轮换/代理（灰色项 · 默认不推荐）
技术直接抬吞吐，但：MB per-IP 限速本意即防分布式规避；代理方可见全部查询词
（隐私红线「数据不出本机」精神冲突）；上游 ToS 风险；个人单机维护代理池成本失衡。
**须用户裁决；多用户场景下隐私面放大，更应拒。**

### B5 本地 MB 数据库副本（倾向拒绝）
官方 dump 数十 GB、导入路径 = PostgreSQL（SQLite 需自研 ETL）；需求侧错配
（30/min 夜窗余量远超所需 + MB genres 覆盖本身稀疏，本地副本不改变覆盖率）；
运维面暴增违背「优先简单、不提前平台化」上游原则。工作量 L。

### B6 缓存与增量续跑补强
现状已有：SearchMemo 正缓存（TTL 10min/FIFO 256/single-flight，search.ts:35-104）+
mb-calibrate 续跑语义（幂等跳过/genres 复用 MBID 直达/--limit 只计需 resolve 行）。
**缺**：① 负缓存——missed 行不落状态（mb-calibrate.ts:186-190 仅计数），每轮重复
resolve 未命中行；② 无熔断（同 B3）；③ 无持久化批次清单。补强 = missed 标记落行内
（alias_sources 附标记或新列，须迁移裁决）或 CLI 本地清单件 + 负缓存 TTL。
工作量 S–M。红线 ✓。

## Q5 · genres 多源合并口径（B1 的核心细节）

MB = 多值带票数（lookup 才有）；iTunes = primaryGenreName 单值粗粒度；
Discogs = genre+style 数组较全。建议口径：**MB 优先（票数排序归一如 ca48ba5 既有
normalizeGenres）→ 空位才由 Discogs genre+style 补 → iTunes 单值最后补（且仅当
前两者全空）**；归一沿用既有 chips casefold 查重词表（防 rock/Rock 碎片）。
