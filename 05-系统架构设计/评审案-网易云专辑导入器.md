## 1. v1 方案全貌（2026-11-14 代码分析，全部经实读核实）

**架构 = 外部 API 网关 + 瘦客户端**（v1 相关五件共 ~1900 行，其中 UI 弹层 934 行）：

```
v1 App (Next.js)                netease-api 容器（docker-compose 自部署）
├── lib/netease.ts   427 行 ──→  api-enhanced（NeteaseCloudMusicApi 增强版），
├── api/netease/qr    58 行 ──→  网易云加密协议/登录/风控全部外包；
├── api/records/import/netease/290 行   NETEASE_API_BASE_URL 默认 localhost:3001
└── netease-import-modal.tsx 934 行      （compose 内走本机代理 7897）
```

v1 自身代码只做四件事（不碰网易云加密）：

1. **三种认证**（`lib/netease.ts`）：手机+密码（code 502 → 需验证码 449 透传）/
   浏览器 cookie 粘贴（服务端 sanitize 去 Set-Cookie 属性）/ **QR 扫码**
   （`/login/qr/key` → `/create` → 轮询 `/check`：801 等待→802 已扫→803 授权得
   `MUSIC_U` cookie→800 过期）。
2. **两种导入源**：收藏专辑 `/album/sublist`（分页 pageSize ≤100，**页间 sleep 200ms**，
   async generator 流式）；歌单转专辑 `/playlist/track/all`（按 `al.id` 去重聚合，
   parsePlaylistId 支持 URL `?id=` 与裸数字）。
3. **两段式导入**（`import/netease/route.ts`）：`preview=true` 拉全列表标 `isNew`
   → 用户在 UI 勾选 → 正式导入（`selected` 键过滤，limit ∈ [1,200]）。
4. **导入管线**（关键）：去重键 = `artist||title` 小写 vs 已有 records → 逐张
   **MusicBrainz `resolveReleaseByArtistAndTitle()`**（带 release-cache + 用户个人
   MB token）→ `createUserRecord(listenAt=网易云收藏时间, personalTags=["netease",
   "auto-import"])` → 逐张 try/catch（failures 前 20 条不阻塞整批）+ summary 四计数。

**设计灵魂：网易云只当「专辑发现源」，元数据权威仍是 MusicBrainz。**

## 2. 与 2.0 的契合度（同构点，直接继承）

| v1 机制 | 2.0 对应 | 结论 |
|---|---|---|
| 「发现源 → MB 权威化 → 落库」 | SourceChain 降级链 + `upsertAlbum` 身份解析 + alias_sources 合并 + F1 快照 | 语义同构，接口现成 |
| preview → 勾选 → 导入 | 「搜索 → 确认 → 添加」闭环（产品红线：人确认） | 两段式保留 |
| `savedAt` → listenAt；`["netease","auto-import"]` → tags | `listened_at` + Tag 体系（用户数据本地生成） | 符「用户数据是资产」红线 |
| `picUrl` 封面 | covers 内容寻址管线（sha256 + immutable + 懒下载） | 直接复用 |
| 页间延迟 / 逐张容错 / fail-soft | 串行限流 + failures 不阻塞 + Discogs fail-soft 先例 | 纪律同款 |

## 3. 移植方案（Q1–Q4 待裁决）

### Q1 元数据路线（核心裁决）——建议 **B**

| 路线 | 做法 | 代价 |
|---|---|---|
| **A（v1 同款）** | 网易云只出 artist-title 对 → 逐张打 MB resolve → `source=musicbrainz` 行 | **零 schema 变更**；但 500 张 @30/min ≈ 17 分钟且打满全局窗口（与 IM-22 多用户场景互斥） |
| **B（建议）** | 网易云元数据**直接建行** `source=netease`（title/artist/picUrl/publishTime 网易云自备），零 MB 消耗；`savedAt → listened_at` 候选 | 需迁移：`0001_init.sql` 的 source CHECK 枚举 + `MetadataSource` 类型扩展（新增 `00NN_source_netease.sql`，DDL 包事务口径）+ `alias_sources` 归一裁决联动（既有待裁决事项） |

路线 B 理由：导入批次天然大（几百张），MB 30/min 撑不住；网易云元数据对个人收藏
够用；MB 权威化可后置为「用户点开详情时按需同步」的既有路径，不丢能力。

### Q2 外部 netease-api 服务定位——建议 **可选依赖（fail-soft）**

不算 npm 依赖（运行时依赖仍 = 2）；未配置 `NETEASE_API_BASE_URL` → 导入功能整体
停用（Discogs 无 token 停用先例）。部署文档登记：需自部署 api-enhanced 容器。
api-enhanced 为第三方逆向实现（灰色），用户知情自担。

### Q3 凭据红线——**cookie 即用即弃**

网易云 cookie 为敏感凭据：CLI/服务端**内存持有、单次导入用完即弃、不落库不写日志**
（2.0 V10 无状态口径）。日志脱敏断言进测试。

### Q4 形态——建议 **CLI 起步**

v1 的 934 行 React 弹层在 2.0 无 JS 基线下装不下；SSR 两段式页（`<dialog>` 岛屿，
IM-15 贴线先例）可行但后置。CLI 先例齐（`seed-dev.ts` / `color-extract.ts` /
`rebuild.ts`）：

```
scripts/netease-import.ts
  --mode saved|playlist --id <歌单ID|URL>
  --auth cookie "<MUSIC_U=...>" | --auth qr            （QR = qrimg data URL
  --preview                                            落本地临时文件打开扫码）
  --selected <dedupKey,...>  （缺省 = 全部新专辑）
  --dry-run
```

输出 summary {fetched/new/exists/imported/failed} + failures 清单（对齐 v1）。

## 4. 落库路径与红线核对

- **写入路径**：复用现有 `upsertAlbum`（身份解析 + alias_sources）+ POST /records
  同构建 Record（`added_at=now`，`listened_at=网易云 savedAt`，tag `netease`）——
  **DAO 零新增方法**（dao.ts 199/200 贴线，导入器不得加方法；如需读捷径走域文件委托先例）。
- **节流**：对 netease-api 的页间间隔提到 **≥1s**（2.0 串行纪律口径，500 张收藏 ≈
  10 页 = 10 秒，无感）；逐张落库为本地 SQLite 毫秒级。
- **封面**：picUrl 交 onAlbumAdded 既有异步钩子懒落盘（500 张 ≈ 30MB 量级，Q4/IM-22
  备份口径联动）。
- **红线**：运行时依赖 = 2（CLI 用 node 内置 fetch，QR 图片写文件零依赖）；RSS 不受
  影响（流式分页）；无 JS 基线不动；落点 = 主线仓 `musicgraphy/scripts/` +
  `src/server/metadata/netease.ts`（瘦客户端 ~200 行）+ 迁移文件（路线 B）。
- **测试**：零网络注入口径（fetchFn 注入假 api-enhanced）：三认证分支/分页拼装/歌单
  去重/dedup 键/preview-导入两段/cookie 脱敏/失败容错，预估 +10 项。

## 5. 容量量化

| 项 | 量级 |
|---|---|
| 500 张收藏拉取 | ≈ 10 页 @1s ≈ 10s（api-enhanced 对网易云的实际延迟另计） |
| 落库 | 500 行 SQLite 毫秒级（单事务） |
| 封面 | ~30MB 磁盘（懒下载，不阻塞导入） |
| MB 消耗 | 路线 B = **0**；路线 A = 500 次 ≈ 17min @30/min |
